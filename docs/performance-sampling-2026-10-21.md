## 改动

### 临时元数据工程复用

`LocalConsonantTimingBackend` 为 `PrepareCoefficient` 的映射工程保留最多五个空闲实例，对应一个最大窗口集合。每次租用先移除旧音符，再更新长度、声库和本次音符；准备对象独占租出的实例，查询结束和过渡路由清理后才能归还。超过上限、准备失败和后端关闭仍执行原生 Close。原生句柄访问继续受原来的后端锁约束，没有把活工程的读写搬到后台线程。

复用不保存计算结果，也不改变 revision、取消、音素边界、时值计划或音频缓存键。这样正常串行发布不再为每个查询立即执行昂贵的原生工程关闭。工程切换或后端退出仍可能需要支付最终销毁成本。

### 参数点删除的 Part 归属

原来的输入观察器不能读取已删除控制器的 `Parent`，因此对 `WIVSMMidiController + DidRemove` 使用全工程保守失效。原生 Pencil 提交会删除旧参数点；一旦工程含有自定义时值数据，这条路径会把其他受控 Part 也加入重新失效集合。

新增 `ControllerRemovalScopePatch` 在原生 `RemoveController` 前记录控制器句柄所属 Part。通知到来时只把该 Part 标脏，禁止访问已删除对象的原生属性；提交、回滚和撤销重做边界清理记录，失败删除撤销记录。原生 Undo 等没有经过该托管删除入口的路径继续保留全工程回退，tempo、全局效果等实际全局输入也仍正常失效。因此这修正了一条明确的跨 Part 放大路径，不代表所有跨 Part 重渲染原因都已排除。

### 原生参数预览与 viewport

- Pencil / Line 仍执行原版坐标裁剪、折返、排序、候选数据生成和提交状态机，只替换经过核对的两处构造器调用。每个 ParameterView 复用一个候选组和最多 8192 个点；超出上限的点不留在池中。不同当前点不得互相别名，重入调用走普通分配，取消/提交清除对 Part 的引用。SDK 方法结构不符合预期时保留原版分配路径。
- 纯 `ControlParameterChanged` 通知保留原生参数列表的同步重建，省去不涉及参数绘图的十个钢琴窗 FastCanvas 的 viewport 遍历。滚动、缩放、Part 切换和渲染通知保持原路径。没有延迟持有可能已失效的原生参数对象。
- 这组 UI 优化沿用现有 `DeferParameterViewUpdate` 开关及运行时保护。

最终版本还通过四个同时存活准备对象、归还后重新租用、重复 Dispose 和 ClearCache 后复用验证。真实 VSM 的删除通知验证了删除前捕获的句柄与提交期间收到的句柄一致，两个 Part 的测试中只标脏编辑的 Part。

同一份以最低 SDK 6.13.1.1 编译的隔离补丁，在 6.13.1.1 / 6.13.3.1 均成功应用七个相关 Harmony 补丁：两个预览方法各替换两处构造器，UpdateView 的十处调用均替换为选择性 viewport 包装。使用只初始化 WPF 基类、没有工程上下文的测试对象执行修改后的入口，检查 JIT 和清理路径；没有声称完整 Editor XAML 或实际拖动交互已验收。

实际 WPF 候选对象的分配对照：预热后 200 次更新，每次 512 个候选点，原版分配 41,940,840 bytes，复用后 65,640 bytes。测试保留相同数据列表与别名检查，并含反射测试支出；这只是候选分配链路的对照，不是鼠标事件或绘制帧耗时。

两个 SDK 均通过原生元数据基准及删除通知检查。整个解决方案使用 6.13.1.1 参考 SDK、独立 artifacts 目录完成 Debug / Release 构建，均 0 警告、0 错误；355 项 McpTests 全部通过。部署使用这份已校验的 Release 合并产物，未重新构建或替换未验证产物。

## 宿主仍需验证

部署后需用同一工程重做参数连续拖动、松开后响应、跨 Part 渲染次数、撤销重做和关闭工程检查；再采相同长度数据，确认长时间 Close 调用是否减少，以及布局和波形快照是否成为下一层瓶颈。原始采样没有每 Part 的事件计数，不能从这份调用栈直接证明每一次额外重渲染都由删除控制器引起。
