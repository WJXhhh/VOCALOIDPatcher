# 版本兼容性审计与整改顺序

## 后续进展

2026-10-17 已实施工程文档与后端分离、未绑定数据保留、timing/选样兼容档案及 C#/Rust 档案握手。随后使用同一产物完成 6.13.1.1 / 6.13.3.1 两套真实组件的限定 SDK 验收，见 [第二套真实组件对照](second-real-version-compatibility.md)。第一阶段记录见 [工程数据与后端分离](project-backend-compatibility.md)。以下审计内容保留为改动前的问题依据，不应把其中“加载即创建 backend”的描述当作当前行为。

2026-10-17。审计当前源码和本机模块元数据，只读检查，没有更改运行逻辑或部署。没有使用第二套 Editor/DSE/VSM 构建进行跨版本验收。

## 结论

近期新增的原生 timing、全音素控制和独立选样后端，目前是**已验证二进制构建专用实现**。已有安全门槛和一些可复用的动态定位能力，但尚不存在贯穿 C#、Rust、宿主数据生命周期的统一兼容层。当前版本的测试通过不能证明跨版本能力。

前面的实现优先完成了当前构建的输入准备、局部规划、真实合成和前端，私有布局依赖随之扩散到查询、宿主和两种语言中。继续按这个方式加入新功能，会使每次引擎适配都需要修改业务代码，也会增加功能之间的契约冲突。这是需要先偿还的技术债。

本机模块版本并不一致：

| 模块 | FileVersion |
|---|---|
| VOCALOID6.dll | 6.13.1.1 |
| DSE.dll | 6.13.1.1 |
| VSM.dll | 6.13.1.1 |
| VDM.dll | 6.13.0.1 |

因此支持标识应是一组模块身份与能力，不能仅用“Editor 6.13”这个字符串。地址使用模块基址加 RVA，可以处理 ASLR；编译后的函数位置、结构布局和调用契约仍然绑定当前构建。

## 现状分层

| 层 | 已有条件 | 当前限制 |
|---|---|---|
| 工程 schema、纯模型、PCM 增益处理、播放时钟算法 | 大部分不读取 DSE 私有结构；补丁自有 ABI 校验版本与尺寸 | 宿主加载、真实边界来源和文件生命周期仍须另行兼容，不能直接把整个功能标成跨版本 |
| Harmony 与 WPF 接入 | 按类型、方法名、参数签名定位，部分私有字段有候选名和空值保护 | 仍直接引用编辑器类型、私有成员和界面生命周期；反射并不自动解决签名及语义变更 |
| 部分原生渲染路由、选样移调 | 有 PE 区间检查、唯一特征匹配、调用关系/RIP 引用解析 | 有迁移基础，仍有布局和调用约定假设，未完成多构建验收 |
| 新 timing/音素 mapper/独立时长选样 | DSE/VSM 整文件哈希、固定 RVA、局部指令签名及自有桥接 ABI 检查 | 当前明确强绑定；函数入口、全局表、字段、步长、虚表和补帧调用点均参与契约 |

`clock ABI 14`、`timing ABI 3` 等验证的是补丁 C# 与 Rust 两端的一致性，不能证明某个 Yamaha DLL 的布局兼容。

## 优先问题与代码依据

### P1：工程数据恢复依赖原生后端可用

调用链：

```text
SampledTimingProjectLoadPatch.Postfix
  → SampledTimingHost.Load（有 timing 数据时）
  → Get / LocalConsonantTimingBackend
  → NativeConsonantTimingEngine
  → LocalTimingNative.VerifyImages
```

恢复异常会走 Load patch 的 catch，关闭刚加载的 sequence 并返回 GeneralError。按此静态调用链，未知引擎构建的拒绝可能扩大到含 timing 数据的工程加载；这不是已在其它版本上动态复现的结论。

应先把文档、历史、归档与后端构造分开。未知构建仍可读取、保留和无损写回扩展数据；执行能力明确显示不可用。含控制的渲染/导出须明确说明尚不能应用这些控制，不能静默忽略后输出看似成功的结果。损坏归档、身份不一致与引擎暂不可用应分别报告。

依据：`SampledTimingHost.cs` 的 `Get/Load`、`NativeConsonantTimingEngine` 构造器、`SampledTimingHostPatches.cs` 的加载 postfix。

### P1：原生构建检查没有覆盖统一入口

`LocalTimingNative.VerifyImages` 固定接受一组 DSE/VSM SHA256。这个检查保护了近期 timing 路径，但同时会拒绝布局实际相同、文件其它内容变化的构建；它也不是全项目通用的原生布局认证。

例如 `NativeVoiceBankHook` 的直接字段写入和虚表槽修改，没有接入同一个构建检查。空指针检查和 catch 不能证明偏移正确。这些早期路径也需要纳入原生兼容边界，而不能只整理新 timing 文件。

### P1：地址和结构知识散落在业务执行器

例子包括：

- `NativeConsonantTimingEngine.cs` 中的工厂、虚表、状态表、mutex、parser、schedule 及 row 布局。
- `ConsonantTimingInputEncoder.cs` 的 VSM 私有编码入口。
- `ConsonantTimingScoreAdapter.cs` 的 72 字节 score 与私有 Part 标志。
- `PreparedPhonemeTiming.cs` 对私有 NOTE 字段的直接访问。
- Rust `phoneme_timing.rs` 的固定入口与 `0x1B3A55` 补帧返回点。
- `duration_bridge.rs` 的固定入口、指令前缀和专用 trampoline 重定位。
- `timing_cache.rs` 的 VSM 私有缓存入口，以及选样工作记录的字段/长度假设。

仅把这些数字搬到一个 Constants 文件，仍然只有一套布局；需要有明确构建身份、能力范围、校验条件和适配实现的 profile。

### P1：安装及依赖还不是完整的功能事务

已有模块会先校验一组入口再安装，但后续分配内存、修改保护或装第二个 hook 仍可失败。部分安装状态有 bitmap，托管端也明确保留 native 模块以避免已安装 detour 指向卸载内存。这不等于所有修改都已回滚。

`Patcher.ApplyPatches` 支持按设置分组停用；部分数据/渲染基础设施处于 featureKey=null 的组。不同功能又共享底层 detour，目前没有统一声明能力依赖、hook 所有者、安装/撤销顺序和部分失败状态。

### P2：验证集中于当前构建和当前素材拓扑

190 项托管测试与既有 Rust/真实引擎测试有价值，但并非跨构建矩阵。研究工具中出现 `6.13.0.1` 字符串或旧报告标题，也不能单独当作另一套二进制已经验收的证据。

近期补帧崩溃、共享边界冲突和 `Sil→f / Sil→7` 接点误判都发生在同一个构建。版本 profile 只能隔离布局变化，还需要覆盖引擎拓扑和功能组合的行为契约。

## 目标结构

```text
UI / 工程文档 / 历史 / 参数语义
                 ↓
           按能力调用的后端接口
                 ↓
      已识别且已校验的兼容 profile
                 ↓
   原生函数、布局、调用点与 hook 安装器
```

profile 必须同时描述模块身份、函数/全局量、结构偏移和步长、虚表/score 形状、调用点与 trampoline 契约。由一份权威描述生成或校验 C# 与 Rust 两侧的数据，避免各自维护相同偏移。业务查询、拖动和归档层不再自行做 `module + RVA` 或私有字段读写。

能力至少区分：原生边界读取、局部 planner、mapper、渲染路由、缓存身份、独立选样、音量处理、工程归档。接口可用、入口定位成功、布局验证成功和行为验收成功应有不同状态，失败说明具体模块和能力。

## 整改顺序与验收

1. **先拆工程生命周期。** 文档可在无后端状态下存活；未知构建、模块尚未加载和真实数据损坏分别处理。验收：后端不可用时工程可打开/保存、控制值和未知扩展不丢失，控制未生效的渲染不会伪报成功。
2. **再建立统一 profile 和能力注册。** 首先完整表达当前已验证构建，保持声音和行为不变；将私有访问收进适配层，并让原生侧也检查所选 profile。验收：当前组合的 PCM/边界/保存/历史回归通过，模拟缺模块、错误尺寸、入口多匹配及安装失败都不会越界执行。
3. **最后引入第二套真实构建。** 优先使用稳定导出；对私有入口使用有界唯一特征、调用关系、全局引用与结构访问约束共同定位。新 hash 可以进入候选识别，但只有满足布局/行为认证才能启用功能。不能删除哈希门槛后，仅凭常见函数序言自动放行。

第二套构建应在独立进程中使用合法的本机安装完成认证，记录模块指纹和能力矩阵；不把 Yamaha DLL 放入仓库。矩阵须覆盖局部查询零合成、真实边界、不同音素拓扑、音量、timing/选样组合、共享撤销、保存重开、原生/扩展混合编辑及多 Part 路由。未知或歧义 profile 保留数据并关闭未认证的执行能力。

完成第 2 步只代表具备适配架构；完成第 3 步并留下实际证据，才能新增一套跨构建支持声明。
