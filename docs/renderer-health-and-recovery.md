# 渲染故障诊断和受限恢复

2026-10-20，新增 `Rendering/RendererHealthMonitor.cs`，在渲染请求、停止请求和观察者派发边界跟踪当前序列。进度事件仅更新时间；不读取 PCM、不查询局部规划、不写日志。观察者派发上下文复用，每个原生事件向多个观察者分发时只计一次；Part 成员表随输入代次刷新。

## 诊断

失败前保留原生取消码、当前和已退休快照的 epoch／执行／缓存计数、音素游标、过渡和独立时长错误计数、输入通知，以及最近 32 条状态事件。失败 Part 的 timing 数值和过渡控制另作有界摘录，保留指纹和必要的音素身份，不保存歌词、工程路径、PCM 或整个工程。临时目录错误还记录目录是否存在及适配器状态。

原生完成回调并不等于成功：注入的 timing 执行错误能够带着“有效波形”标记进入完成回调。因此原生失败证据必须在原有补丁撤下快照之前捕获，后续不能只根据波形标记把它判为过期错误。普通输出标记尚未有效则允许在延后检查时重新核对。

日志位于 `%APPDATA%/VOCALOIDPatcher/diagnostics/renderer.jsonl`。后台队列上限 32 条，单条有长度上限，文件按约 2 MiB 轮转，保留当前文件及两份旧文件。MCP `timing_diagnostics` 中的 `timing_host.renderer` 提供最后故障与恢复状态。托管未处理异常会尽力同步记录最后一个故障和状态边界；这不保证捕获原生访问违例或进程立即终止。

## 自动恢复

设置项“自动恢复渲染失败”（`RendererAutoRecovery`）默认开启，可以关闭自动重试而继续保留诊断。

1. 原生取消或异常完成先保留故障，待观察者回调退出，再检查序列是否仍打开、输入代次是否匹配、Part 是否仍属于该序列。
2. 只有原生任务全部结束、没有待提交事务和鼠标捕获时才允许恢复；不把正常取消、暂停、内存不足、声库不存在或未知错误盲目当作临时故障。
3. 每轮输入只重试一次，每个序列每分钟最多自动尝试三次。失败后的 Part 身份继续保留，下一次真实编辑可重新检查，避免只恢复当前音符而永久遗留另一个失败 Part。
4. 停止已结束的渲染服务，必要时重建经过哈希认证的临时目录，释放并重建补丁拥有的局部规划后端，重新校验及发布原有控制。规划代次随重建推进，已有候选因此失效，工程数据和撤销记录保持原样。
5. 仅对失败或被该次序列停止打断且仍无有效输出的 Part 使缓存失效；原生会新建本次合成所需的任务上下文。有效 Part 继续使用原缓存，不清空整首歌或重建全局 DSE 管理器。
6. 重试再次失败后停止自动尝试并保留原因。30 秒无进度先记录现场；若原生仍报告未结束，不强行调用会等待原生线程返回的停止函数。若已结束但没有有效输出，可以进入同样受限的重试流程。

这里的“重启”指渲染任务和补丁拥有的规划后端。不会退出编辑器、重载用户工程、销毁被其他 Part 共用的全局引擎管理器，或放弃自定义控制去生成原始声音。原生线程真卡住或进程直接崩溃时，进程内恢复有明确能力边界。

临时目录的私有布局读取收拢在 `ConsonantTiming/Backend/RenderTemporaryDirectory.cs`，只对已认证的 6.13.1.1 / 6.13.3.1 组件开放，且仅创建验证过的 VSM 序列子目录，不修改原生字符串或递归删除目录。未知版本仍可诊断，但不会猜测该字段位置。

## 验证

独立验证入口：`--transition-host-probe`，设置 `VOCALOID_RENDER_HEALTH=1`，`VOCALOID_RENDER_HEALTH_CASE=temp|native|watchdog`。必须使用已经隔离 VSM 应用 ID 的新版探针。

- 两套真实 SDK 均验证临时目录真实丢失、两个 Part 自动重建、持续故障仅尝试一次、后续编辑继续渲染和撤销安全。
- 两套 SDK 均用原生非法过渡推进输入触发 timing 失败，确认重试重新发布正确控制，失败 epoch 被保留且未被“波形有效”标记掩盖。
- 普通采样序列没有 timing 文档时也能恢复，不额外建立 timing 文档。
- 合成的延迟取消回调不重启已有效的结果；繁忙调度器的无进度分支只诊断，随后正常启动仍能渲染。无进度分支通过测试时钟到期验证，未人为卡死真实引擎线程。
- 托管策略测试覆盖单轮限次、跨编辑熔断、取消分类及后端释放重建。

最终 282 项托管测试通过。以最低 SDK 构建的 Debug 解决方案和 Release 合并产物均通过；Release 原生链接器输出被构建任务列为两条警告，没有错误。

所有验证均使用独立构建与独立进程，没有部署到当前编辑器。PCM 可重复性问题仍按先前约定暂缓。

## 同日追加：过渡操作后的宿主故障

用户报告当前会话调整两端过渡菱形或音量会稳定停止渲染。读取该会话的完成／准备拒绝记录后，确认完成回调之后出现了未抛出的 `InvalidOperationException`，但旧日志仅保留异常类型，不能区分执行失败与缓存身份未消费。不能据此断言原生合成已崩溃，也不能把一次成功重放当作现场修复。

这次已确认并修正诊断链自身的两个缺口：

- 编辑器启动会全局初始化独立时长适配器，未使用独立时长的 Part 没有对应快照；原生状态查询返回 `-2` 是“没有该 Part 的快照”。旧诊断把它当作异常，丢弃先前读到的 timing／过渡计数；健康检查还会因此在完成回调内提前退出。现在提供独立的可选状态查询，各路计数分别保留，未知查询错误仍明确记录来源。
- 完成校验生成的异常没有抛出堆栈。现在为执行失败、独立时长执行失败、缓存身份绕过分别保留固定代码及当时的计数快照，不记录任意异常消息或用户路径。

通过一次只读进程转储提取当前 `m u` 的三个接点偏移和身份，已在独立进程按原值重放，并继续从后台规划线程编辑起音／收尾表现、两端过渡增益及重复 VEL。测试匹配编辑器的全局时长适配器初始化和分块设置。独立验证入口为 `VOCALOID_TRANSITION_FRESH=1`，可用 `VOCALOID_TRANSITION_CAPTURE` 指向本机提取的模型 JSON；这些本机文件不进入仓库。修正播放器尚未创建时平滑后端的空实例重绑定，避免独立宿主在该生命周期抛出异常。

这组原值对照没有重现用户报告的停渲染，旧完成回调串代也尚未得到证实。原始故障根因仍未确定；当前修改是诊断和恢复观察修复，不是通过放弃控制值或放行未验证音频来消除报错。新增的真实引擎故障注入覆盖“全局适配器已加载、当前 Part 没有时长快照”的场景，确认实际 timing 失败计数能够保留并完成原有受限恢复。此轮未部署、未关闭或重开编辑器，提取后删除临时进程转储。

## 同日后续：已复现并修正 REG 输入遗漏

诊断版部署后，用户手动复现，MCP 和结构化日志确认 `m → u` 的完整右侧素材与 `phase=-0.203` 在正式合成中两次被拒绝；音素映射自身没有失败。自动重建后的第二次执行仍失败，说明不是单纯的渲染任务失效。完成回调依然带有效 score/wave 标志，不能据此判成功。

关键差异来自工程中该音符保存的 **REG=+1**。前一轮独立宿主没有安装 REG 工程加载补丁，遗漏了这份选样输入；仅加载原生 sequence 和过渡归档不能代表完整工程重放。补齐 REG 加载及正式发布后，独立进程复现了与用户现场完全相同的游标：起音原始半段 `2/6`、中间 `7/17`、收尾 `12/2`；遗漏 REG 时分别为 `2/5`、`8/12`、`21/2`。不能把此前成功的重放视为排除了引擎问题。

根因是局部规划没有携带逐音符 REG，而正式渲染已应用 REG。双方选中不同素材，过渡分段与源推进目标因此不一致；菱形或增益首次需要验证具体 ART 时，正确拒绝了这个不一致的输入。修正包括：

- 捕获逐音符 REG，并纳入局部输入指纹。原生新增独立、不可嵌套、线程局部的只读规划作用域，以已捕获的时间、时长及原始音高匹配 REG，复用正式选择器，不改音符音高或工程数据，也不借用其他 Part 的可变校准状态。
- 音素、过渡、起音参考及独立时长合同的各条规划路径均传入同一份输入；有局部原点时同步平移 REG 匹配坐标，时长合同路径使用全 Part 坐标。
- REG 修改和共享撤销／重做先撤下旧 timing 路由，再发布新的 REG，随后使规划代次和受影响 Part 失效，防止排队重绘先使用旧选择器或旧规划。
- 原生保留首次合成拒绝的预期／实际 ART 身份、帧和源进度位。该附加诊断不改变现有控制 ABI；旧 native 没有此可选导出时仍能读取原计数。非零 REG 的新规划需要新增规划导出，不能静默按 REG=0 执行。

回归保存重开还确认了另一处生命周期错误：REG 延迟重建在后台等待之后，没有在 Dispatcher 内重查代次及所属序列，可能在旧工程关闭后访问已释放 Part。现已在实际执行前重查，并通过关闭后立即重新加载的回归。

6.13.1.1 与 6.13.3.1 的真实 DSE/VSM 各通过 45 轮测试，包含原故障组合、两端 phase／增益、连续 VEL、REG `0/±1/±12`、共享撤销重做、保存重开、两个不同 REG 的 Part 同时渲染及交错 VEL。52 项 Rust 测试、282 项托管测试通过；Debug 解决方案与最低 SDK 的合并 Release 构建通过。原生故障注入也验证新增首次差异证据在路由撤下前被保留。

验证入口仍为 `--transition-host-probe`：`VOCALOID_TRANSITION_FRESH=1`，`VOCALOID_TRANSITION_SOURCE` 为本机故障工程，`VOCALOID_TRANSITION_CAPTURE` 为捕获的过渡 JSON，`VOCALOID_TRANSITION_REG_MATRIX=1` 开启组合及往返验证。各探针独立保存诊断，不能写入真实宿主日志。私有工程和复现控制文件不进入仓库，探针失败产生的临时转储已清理。

本节记录的是独立真实引擎回归。根因修正版尚未替换正在运行的编辑器，宿主仍保留旧诊断版的故障状态；需要同时更新主补丁和 native 后再进行宿主验收。PCM 可重复性问题继续单独记录，不把本次渲染成功当作其结论。

### 部署后首次加载检查：临时序列关闭误清 REG

随后按用户授权部署两个 DLL 并启动原工程。新主补丁与 native 均成功加载，但首次渲染触发了一次真实故障及自动恢复。新增差异记录明确给出帧 3510 的预期 ART `[3510,3555,39,24,0,0]`，实际为 `[3509,3544,39,24,0,0]`；REG 日志同时显示正式渲染时路由 epoch 已变为 0。不能把自动恢复成功当作本次首次加载验收通过。

原因是既有 `RegisterShiftSequenceClosePatch` 在任意 `WIVSMSequence.Close` 前调用 `DisableNative()`，全局清掉所有 REG 路由。新增规划作用域正确捕获 REG 后，规划临时映射序列在释放时关闭，其 Close 补丁把真实工程刚发布的 REG 一起清除。此前独立宿主没有加载这条 Close 补丁，遗漏了这一生命周期条件。

Close 补丁现改为关闭前仅捕获该序列拥有的音符／Part 句柄，在原生关闭成功后逐项释放这些对象的 REG 数据、路由及重建代次；关闭失败不撤下仍存活对象的路由，不再全局清理其他序列。独立宿主加入正式 Close 补丁，并新增“全程不得发生故障或自动恢复”的验收条件。两套实际 DSE/VSM 再次各完成 45 轮组合及保存重开测试，保留的失败计数为 0，LastIncident 始终为空。

这一补充只改变托管 Close 生命周期，已部署的 native 不需要再次修改。新的合并主补丁需在编辑器退出后替换；首次加载的宿主验收在替换前仍未完成。

用户再次退出编辑器后，已部署补充主补丁并核对主 DLL／native 哈希，宿主 MVID 为 `817c9fcc-e3ed-4a28-a837-78070f405cfe`。原故障工程正常打开，渲染启用且完成、score/wave 有效，无挂起、无故障及自动恢复记录。但该次打开命中了有效缓存（epoch 1、scopes 0、cache keys 1），只能确认加载及缓存复用正常，不能声称新合成已验收；过渡拖动后的真实合成仍待用户手动触发并读取 MCP 状态。

用户随后手动拖动过渡，并回复“已操作”。同一宿主 MCP 读取到 revision 14、native epoch 2、scopes 1、transition calls 466、applied 180，原生／过渡失败计数均为 0。渲染服务启用、渲染已完成、score/wave 有效，渲染健康状态无 incident、无失败或自动恢复记录；音素投影边界与原生边界仍均为 `[-76,-4,476]`。这次已有实际新合成及控制消费证据，补齐该 `m u`／REG=+1 故障组合的宿主手动操作验收。没有通过保存工程、清除控制或自动重试来得到这一结果。
