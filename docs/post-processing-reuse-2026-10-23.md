## 发现与修改

普通提交及撤销/重做调用音素音量、过渡平滑的 SourceChanged，原先对本 sequence 的所有已跟踪 Part 都清空缓存并重新排队。即使源音频和参数未变，稳定期结束后也会重新生成 WAV。与 Comp 自有源缓存不同，这是普通 Part 的派生文件处理。

现在每个 Part 最多保留一份不对外发布的候选结果。捕获新请求后，按以下完整输入比较，匹配且成品文件存在才重新发布该结果：

- 两层都检查上游路径、文件长度和最后写入时间。
- 音素音量额外逐项比较真实时间区间和每段增益，保留重叠区间顺序。
- 过渡平滑额外逐项比较 junction 坐标、左右增益和完整配置。

候选缓存不会被 Substitute 读取；确认前维持原有回退路径。原生 RenderStarted 同时清空活动结果和候选，不能用“路径、长度、时间戳碰巧一致”跳过新渲染。导出使用相同的完整比较；当前代次、处理锁、发布前检查和 DSP 运算均保留。文件清理保护正在比对的候选，新结果替换后及关闭时释放；音素音量恢复中性时直接回退并清理旧结果。

| 场景 | 音素音量文件处理，前 → 后 | 平滑文件处理，前 → 后 |

| 两个 Part，十次输入未变通知 | 20 → 0 | 20 → 0 |
| 只改第一个 Part 的音素音量 | 2 → 1 | 2 → 1 |

每次通知之间都等上一轮结果完成，因此计数变化不是靠把十次通知合成一次。单 Part 修改后，另一 Part 的结果路径保持不变。这里统计生产 Host.Process 的实际文件处理调用，没有把全部后台工作都算成零。

验证只屏蔽没有宿主对象的 AudioPlayer/钢琴窗刷新，并通过 TransitionView 提供从真实原生查询得到的固定执行计划；实际捕获、去抖、代次、锁、DSP、文件、撤销/重做和导出路径正常执行。它不代表完整 Editor UI 或回退规划的端到端验收。

不同独立原生进程生成的夹具摘要有差异，未声称跨进程 A/B 原生音频逐字节相同。每个进程内部检查无变化通知前后的摘要一致；优化版另在相同输入上直接重跑未修改的 DSP，四份成品及一次 Undo 恢复结果均与新算参考的 WAV 摘要一致。
