# 短静音桥接压缩后的原生游标恢复

2026-10-20。继续排查 `s t ei AU` 的 `s/t +1 帧` 和 `t/ei -1 帧`。此前默认布局锁死已部署修复，本轮修改尚未部署。

## 原因

报错 `Native phoneme mapping failed` 来自本补丁 `NativePhonemeTiming.End` 对 Rust 状态的检查，不是 DSE 返回的最短时长限制。独立重放捕获了如下状态：

| 请求 | 回退后的输出帧 | 原检查点中的源帧 | 原生采样段数 | 实际重新进入的源帧 |
| --- | --- | --- | --- | --- |
| s/t +1 | 3295 | 3294、3295 | 7 | 3295 |
| t/ei -1 | 3294 | 3294、3295 | 7 | 3295 |

压缩将 `Sil→t` 的内部 split 与 end 取整到同一输出帧。随后 NOTE 到来，DSE 撤回尾部旧规划，输出末端从 3386 回到 3295 或 3294。原算法只按输出帧匹配所有 begin/split/end 检查点，发现两个不同源帧后，按既有安全规则拒绝恢复位移，最终报 Reason=1。首个错误出现在重新提交 `t→ei` 的 1/15 帧输入；最终状态里的 Left/Right 还会继续被后续调用更新，不能把最后显示的 24/2 当作首个失败素材。

当前 Ghidra 只读目标为旧版 DSE.dll，SHA256 `7A4965BD377DBC2B08710E807AE1345B67D9FFF6579CA0C01A769F744366F5B5`，x64，基址 `0x180000000`。原生 allocator RVA `0x18B630` 每追加一个实际 work item 更新 `ScheduleMappedCount`，末端查询 `0x18ABA0` 读取实际尾部段的 End。运行期捕获的 count 和末端与上述回退相符。

## 修正

- 每次合法映射保存“原生段数、输出起点、源起点”的精确派发检查点。真正观察到输出末端回退后，优先使用这个此前实际出现的派发身份，消除 split/end 取整造成的歧义。
- 没有派发证据时，保留原来仅接受唯一源帧的边界检查；未知和冲突仍拒绝，不猜最大/最小源帧或逆插值。
- 原生段数减少也可能是前端已消费段被回收，不能仅据 count 变小推断回退。仍要求实际输出末端后退。新增模型测试单独覆盖这一点。
- 新历史每个 parser/context 最多 128 项，随真实 schedule 清空，保留错误累计；不跨 Part、parser 或 render scope 共享可变游标。导出接口、ABI、工程格式和控制值不变。
- 游标修正后还暴露出一处不完整的托管证据约束：`Sil→t` 的 t 半段可以量化为零，但紧接的 `t→ei` 仍含有非空 t。现在只有在后段首尾严格相接、From 确为 t 且 t 侧区间非空时才接受这条接续；没有无条件接受零长音素。

移除了研究用临时跟踪输出，没有把逐映射日志加入正式热路径。

## 验证

同一最低 SDK 编译的 harness、候选 Release 原生库，分别运行真实 6.13.1.1 / 6.13.3.1：

- 每版五个基线、40 个双向候选全部通过；原来两次拒绝均成功完成真实渲染，原始 VSM 边界逐项吻合，PCM 改变，Failures=0。
- 每版 40 次中 36 次原始位置直接相等，另 4 次是既有的首元音后移后空 score 情况，需要既有的已验证投影；40 次实际已消费采样边界全部吻合，不把空 score 算成原始位置一致。
- 局部候选查询的 Start/Step/Samples 全为零。恢复原值后的 PCM 与温态基准逐字节相同。
- 选样/VEL/浮点/timing 组合 20 次通过；既有共享接点、重置、撤销重做及保存重载回归通过。
- 既有四 Part、三轮同时渲染 12/12 PCM 与顺序参考一致，峰值三个原生作用域重叠。
- 两端 ±80 帧和零偏移的三类补帧崩溃回归，共 27 请求；11 次合法渲染和 88 次强制补帧通过，16 请求仍由既有边界约束拒绝，没有进入合成。
- 50 项 Rust、262 项托管测试通过；最低 SDK 的独立 Debug/Release 全解决方案构建成功。Release 的两个既有警告为 Rust 链接器输出编码警告。

### 额外并发测试的限制

新增的中文五音符四 Part 探针，三轮共 12 次均完成，边界与顺序参考完全一致、原生 Failures=0、峰值三个受控 scope。但 **PCM 逐字节比较仍失败，探针保留退出码 1**，没有设置容差把它变成通过。

同一探针不发布任何 timing 控制时，已部署旧原生库也出现 12/12 不相同；候选库的无控制对照为 11/12 不相同，边界仍全部一致。这说明该现象在本次新游标逻辑未介入时也存在，尚不能归因于本修正。一次受控对照中的最大单样本差为 6–11 个 16-bit PCM 单位，差值 RMS / 原信号 RMS 为约 0.00016–0.00056；这只是观测，不是验收阈值或“不可听”结论。该项并发 PCM 确定性尚未解决，不能宣称新增中文夹具已完成逐字节验收。

入口为 `--compound-boundary-probe`；`VOCALOID_COMPOUND_CASES='1:1:1;1:2:-1'` 只重放两次原始错误。`VOCALOID_COMPOUND_CONCURRENT=1` 开启上述并发探针，`VOCALOID_COMPOUND_CONCURRENT_CONTROL=ordinary` 运行无控制对照。相邻渲染覆盖同名 WAV，输出复用同一本机工作目录。

证据：[phoneme-timing-quantized-rewind.json](evidence/phoneme-timing-quantized-rewind.json)。安装主补丁与原生 DLL 哈希保持上次部署状态；没有操作用户工程或启动/关闭 Editor。
