# 采样声库逐音素 timing

2026-10-17。已实现原生执行器和 Emotion 内的全部音素边界拖动，并持续修复用户实测发现的问题。当前执行 ABI 为 3；最新的双边界、流式补帧、引擎归属和缓存身份验证见文末。隔离引擎验证不能代替真实 Editor 手势验收。

## 操作与数据

N 个音素提供 N+1 条边界，包括首音素开始、所有相邻音素的交界及最后一个音素结束。相邻音素共用交界，不人为制造空隙。每条线都可横向拖动，悬停显示交界两侧音素和相对音符起点的毫秒值。Ctrl 单击或双击复位该边界；Escape、失去捕获、切换 Part 或源修改取消候选。

拖动只维护候选，约每 33 ms 查询最新目标，不在 MouseMove 修改工程或合成音频。松手验证上下文后提交一条共享历史记录，正常音频渲染只在提交后请求。候选显示经过原生规划验证的边界，禁止交叉、压成零长及超出已捕获上下文。

沿用 VPR 的 `VOCALOIDPatcher/sampled-timing.json` schema 1。`phoneme.boundary.offsetSeconds` 的索引扩展为 0..N，保存相对默认原生边界的秒偏移，并与既有浮点系数共存。`transition.offsetSeconds` 及未知轴仍保留存储，执行时明确拒绝；当前支持过渡交界的位置，不代表另有独立的过渡宽度控制。

## 两条兼容路径

把第一个元音推到乐谱音符起点之后时，原生采样映射和音频可正常生成，但 VSM 可能不再关联该音符的 score，返回空边界。本次中日文各一例都观察到这一行为。宿主在发布时缓存原生规划验证的位置，投影到 `GetPhonemePositions`、`BeginPhonemeTick` 和 `EndPhonemeTick`；绘图访问器内不查询引擎。该投影已构建，**尚未做真实 Editor 验收**；隔离证据对这两例明确标为 `needsProjection`，没有把空数组算作 VSM 边界一致。

另一个问题是新载入的 Part 可以命中 VSM 全局缓存，完全跳过携带 timing 的 render core。现在在原生缓存键中加入受控 Part 的不可变数值快照摘要，读取快照 Part 与写入实时 Part 使用相同身份。没有控制的 Part 保持原键；不清空全局缓存。旧的“先载入缓存，再用 ScoreEdit 失效并重渲染”路径已撤除。命中包含 timing 身份的缓存时允许零 DSE 合成完成；详细实现及验证见文末。

## 2026-10-17：提交后渲染服务停滞的根因修正

上一修复部署后，用户再次报告移动音符后旧波形和曲线停留。现场只读诊断显示普通 `l a`、VEL 64 的音符已移动，宿主持续处于渲染中；timing 会话没有 fault、没有 suspended，旧记录已脱离。这说明异常降级没有解决真实故障。

本轮把隔离探针改为 Editor 的常驻渲染服务生命周期：首次启动服务后，原生 Commit、Undo/Redo 和 timing 提交均只泵送 Dispatcher 与原生观察器，不再由测试为每步补调用 StartAsyncRendering。旧实现稳定卡在首次 VEL 修改。此前每步手动 Start/Stop 的测试掩盖了生产流程缺口，不能用于宣称该路径通过。

核实并修正了三处相连的问题：

- `CanAsyncRendering()` 返回服务当前是否启用；实测 Start 后为 true、Stop 后为 false。它不是启动许可。原代码停掉服务后又以该方法为条件重新启动，导致启动分支永远跳过。
- 原生 Commit 会唤醒已启用的渲染服务，并不再次调用托管 StartAsyncRendering。原代码只因源编辑停止服务、清理路由，却在自定义文档值未改变时没有排队重新发布和启动。现在 VEL、移动、删除、撤销等源修改也排队合并更新。
- 仅在 Commit 的 postfix 停止仍有竞态：原生工作可能已完成，Stop 会丢掉刚产生的完成通知。隔离测试中移动后出现“服务已启用、原生已完成，但没有完成回调”。现在在 Commit prefix 暂停旧服务和路由，提交后发布新快照，再启用服务；缓存失效自身的 Commit 以 Rebuilding 标记排除重入。每次真实源变更重置该代次缓存修复额度。

改正后的探针覆盖连续两次 timing 提交、VEL 0/100、原生 VEL 撤销/重做（音频哈希恢复）、连续 12 次提交、移动后重新设置 timing、删除最后音符。所有正常控制用例保持 suspended=false、实际原生路由有效，完成后服务启用且渲染结束；每步均收到真实完成通知。移动后的旧计划仍采用前述脱离规则，本轮没有实现自动绑定迁移。另保留单独的故障注入恢复用例，不能用它替代正常 timing 执行验收。

最终 Debug/Release 全解决方案构建和 150 项托管测试通过。隔离探针仍未包含真实 WPF 波形缓存及共享历史协调器，真实宿主手势和画面需部署后核对。摘要：[timing-commit-lifecycle-validation.json](evidence/timing-commit-lifecycle-validation.json)。

## 2026-10-17：大幅左拖首音素的原生坐标失配

用户实测 `s\ i_n n` 的第一条边界大幅向左拖动后失败。现场显示渲染已结束，但 timing 因原生执行错误暂停，真实音素边界为空。按现场音高 61、VEL 38、位置 960、长度 540 重建隔离工程，旧实现从首边界额外左移 20 帧（约 116.1 ms）开始稳定出现 6 次映射错误；局部查询仍返回有效边界，因此只检查查询或恢复普通渲染不能修复该问题。

DSE 在正式规划前会建立临时 schedule，随后撤回末段。大偏移使临时的一帧分配发生量化压缩；167 帧原始坐标只推进到 166 帧，补丁保留了 -1 的 displacement。原生逐段撤回至空表后从零重新规划，而补丁的有限检查点已经淘汰原点，因而把合法重建误判成非法回跳。小偏移没有发生这次压缩，旧的零位移启发式恰好掩盖了问题。

本轮依据已验证 DSE 映像的原生 segment count（schedule + 0x34）同步状态：空表开始映射时清理 displacement、last_actual 和检查点，保留整个 render scope 的调用及错误计数。计数为空与“末尾坐标为零”不同，不能把量化后的零长度片段当成重置。非空表撤回仍只接受已观察且无歧义的检查点。没有新增 reset 函数 hook，没有放宽失败检查或扩大可拖动范围。另外，渲染上下文须匹配已绑定 parser/schedule 及当前 scope，避免未绑定临时表或复用引擎的旧绑定使用当前 Part 的 warp。

## 2026-10-17：双边界、流式调度及缓存身份修复

这次修正三处原生执行问题：

- 流式解析器在合成时钟追上队列末端时，会补一帧输出静音。这不是源音素时长，不能再次经过 warp，否则某些尾端调整会把必需的一帧压成零，导致原生访问空片段。只辨识已验证映像的该调用位置；其它前置静音仍参与映射，局部规划查询保持原有行为。
- 同一 Part 可以建立多个原生引擎。每个 parser/schedule 单独持有游标和检查点，仅共享不可变锚点；Start 与 AddEvent 都刷新归属。不能让另一台引擎初始化时清空本引擎的位移。
- 已释放引擎的 schedule 地址会被新引擎复用。旧代码先按该地址从 HashMap 找一项，再检查 epoch/scope，可能随机挑到旧项并遗漏前置静音映射。现在绑定时移除该地址的旧归属，查询时再核对当前快照。回归实际观察到地址复用，已增加确定性的所有权测试和复用计数。

原生依据仍为上文固定 DSE/VSM 哈希。DSE allocator RVA 0x18B630，静音入口 0x1A7310，流式解析的输出补帧返回位置 0x1B3A55。Ghidra GUI 目标切换前后都核对了目标名称、哈希、x64 架构和基址；没有修改分析项目。

缓存链路改为真实身份，而不是先命中错误缓存再重渲染：VSM 缓存键 RVA 0x091EE0，读取准备入口 0x060640，关闭发布入口 0x08D900。对受控 Part，原生键再与版本标签、NOTE 的时值/音高/浮点系数以及全部 warp 锚点的 SHA256 摘要组合；不包含指针、epoch 或可变游标。读取阶段用有作用域的快照→源 Part 路由，写入阶段使用源 Part，支持并发，普通 Part 的键不变。相同数值跨撤销、重开和进程保持相同身份。

撤掉 `BeginScoreEdit/UpdateScoreEdit/EndScoreEdit` 失效路径。反编译确认它修改已有的音高 score，空 score 或帧数不匹配会失败，并非通用时值失效接口。真实 timing 提交仍只暂改再恢复最多 33 个上下文 NOTE 后提交一次无历史原生修改，正常 PCM 工作范围由 VSM 决定；候选查询不合成音频。加载时先发布正确缓存身份，允许直接命中对应的缓存。关闭工程时保留路由直到原生发布完缓存，再用预先捕获的指针清理；旧代码在原生 Close 前撤路由，会把受控音频按普通键保存。相同控制值的重复提交也不会再先停掉渲染服务。
