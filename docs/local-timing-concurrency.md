# 局部时值查询：并发、取消与生命周期验证

2026-10-16。本轮在隔离进程中，让正常 VSM 异步音频渲染器与局部时值后端同时工作，并测试同一 Part、不同声库、锁竞争、取消和关闭。**原生同进程测试通过；这不等于真实 Editor/WPF 宿主验收通过。** MCP 查询没有发现运行中的 Editor，本轮没有部署或启动 Editor，也没有接回鼠标拖动。

[并发数值证据](evidence/local-timing-concurrency.json)包含失败见证、修正后测量、源码及二进制哈希；[会话复用后的准确性与性能证据](evidence/local-timing-reused-session.json)包含完整 142 组边界对照及 512 个起点对照。早期实现及原始输入/坐标方案见[独立后端报告](standalone-local-timing-backend.md)，其逐候选 Start/Stop 与性能数值已由本报告更新。

## 找到并修正的两个问题

第一个问题是锁等待发生得比保护更早。旧实现进入 native Start 后才等待规划 mutex，而 native Start 自己可先等待同一个全局锁一秒。另一个线程故意持锁时，查询实测阻塞 **1089.87 ms**，所以旧版本“规划锁等待 50 ms”不能理解为完整查询有这个上限。

把同一个锁提前持有并覆盖整个 Start 虽能及时拒绝繁忙请求，却造成第二个问题：Start 会分配、初始化合成状态，连续查询在此期间占用全局锁，饿住正常渲染。反例中串行渲染 **329.15 ms**，持续查询时变成 **11329.27 ms**。音频内容仍相等，但性能不合格；这条做法已经撤回。

最终实现把 Start 移到私有会话构造时，只运行一次。每个候选窗口在短锁内依次重置 schedule 与事件解析器，再规划、映射和释放；不重新启动或停止合成状态。私有会话销毁时才 Stop、Release。直接规划所需的调度表与解析器重置按当前 DSE 原生初始化链核对，之后用完整真值矩阵验证；没有复制反编译源码。

原生入口均受精确哈希保护：schedule reset 为 DSE RVA `0x18BE00`，parser reset 为 `0x1B4D60`，事件规划仍为 `0x1B2AB0`。Start 与规划 mutex 身份一致也在构造时检查。等待采用 5 ms 分片，累计预算 50 ms，并检查取消；本轮受控锁竞争的完整查询 **58.18 ms** 返回 Timeout，释放锁后可继续查询。此预算针对查询中的规划锁等待，**不约束冷构造、销毁和系统调度，也不是整个查询的硬实时上限**。

## 正常渲染共存

先用两个独立的 48 音符工程建立串行参考，确认全部音素边界和 WAV data 区 SHA-256 完全一致，再建立同样的工程运行并发模式。下表的“实际重叠”只计查询期间 PCM Step 确实前进的成功查询，不把尚未派发 Completed 回调当成渲染仍在计算。

| 模式 | 成功查询 / 实际重叠 | 正常渲染总耗时 | 查询中位数 | 查询最大值 |
| --- | ---: | ---: | ---: | ---: |
| 串行参考 1 / 2 | — | 413.03 / 347.77 ms | — | — |
| 同声库、另一 Part，不限频压力 | 1042 / 782 | 757.56 ms | 0.65 ms | 42.75 ms |
| 正在渲染的同一 Part，不限频压力 | 411 / 357 | 804.07 ms | 1.71 ms | 43.60 ms |
| 另一采样声库，不限频压力 | 1050 / 795 | 744.81 ms | 0.63 ms | 41.48 ms |
| 同一 Part，每秒最多 60 次 | 13 / 8 | 378.75 ms | 2.37 ms | 38.72 ms |
| 渲染中关闭、重建查询后端三次 | 87 / 78 | 559.12 ms | 0.65 ms | 8.85 ms |

五种模式的 **48 个音符完整边界列表与 PCM data 哈希全部等于串行参考**，正常渲染的 PCM Step 数也都为 4431。不同声库使用 MIKU 渲染、RIN 查询。同 Part 测试保持源音符和控制参数不变，让原生 renderer 自己更新结果；没有用候选 VEL 修改源 Part。

不限频压力仍明显争用 CPU/锁。60 Hz 的试验是研究 harness 的请求节奏，不代表产品里已经有请求调度器。查询峰值仍接近 40 ms，未来必须合并为“只保留最新请求”，在合适的线程及源快照/生命周期保护下执行，不能把同步方法直接塞进 MouseMove 或无限排 Task。

三次关闭并重建各耗时约 157–172 ms，期间正常渲染均有 PCM 进展。因此会话应常驻复用，关闭和重建不应成为每次手势或每次切换音符的动作。

## 取消、关闭与内存

- 人为持有原生锁后，在查询已经进入后端 gate 时测试：同后端第二次调用 **0.68 ms** 返回 busy；取消中的调用 **18.20 ms** 退出；同时请求 Dispose，待查询退出后完成关闭。关闭后的调用拒绝访问，替代会话的查询结果与关闭前一致。
- 用同一个后端完成 30 个私有源 sequence 的查询、切换和关闭，交替使用 MIKU/RIN；源由拥有者在查询结束后关闭。**没有测试一边释放源指针、一边继续使用它**；宿主接入必须遵守这个所有权条件。
- 两个后端分别在线程上并发查询不同声库，各 60 次，120 次均等于各自串行结果。测量阶段 Native Start、PCM Step、Samples 均为 0，说明窗口重置没有再次进入冷启动或合成。
- 另外持续执行 8000 次强制缓存未命中的查询。1000 次后至 8000 次，进程私有提交内存只增约 112 KiB，托管存活内存增约 6.2 KiB，句柄和线程始终为 359 / 9；4000 至 8000 次私有提交内存相同。最初 1000 次高水位约增 16.8 MB，不能隐去。此测试未观察到按请求持续增长，但不构成所有场景下无泄漏的证明。

## 准确性与单独查询性能复验

会话重置方式改变后，重新运行完整对照，不沿用旧版本的准确性结论：142 组完整边界逐 tick 相等（含 3 组原生空结果），512 个 VEL 起点全部相等；源状态不变，候选 PCM 为 0，帧位置保持 0。测试配置和上下文上限保持不变。

| 无音频候选查询 | 中位数 | p95 |
| --- | ---: | ---: |
| 142 组混合上下文 | 0.86 ms | 1.87 ms |
| 512 个独立参考起点 | 0.13 ms | 0.32 ms |
| 300 次三音符上下文，强制未命中缓存 | 0.17 ms | 0.19 ms |
| 100 / 1000 / 10000 音符工程，百万 tick 空尾 | 0.63 / 0.64 / 0.63 ms | 0.73 / 0.94 / 0.72 ms |

长工程仍只消费 9 个上下文音符、3 次规划；1000/10000 音符工程只做性能测量，不为此生成全 Part 音频。冷会话初始化约 151 ms，单独查询测试不包含这个一次性成本，也不包含 UI 和线程调度延迟。

## 真实 Editor 接入前还需满足

当前没有修改 overlay、拖动提交路径、设置或 MCP 接口。后端仍是同步内部组件，真实 WPF Dispatcher、Editor 撤销/切换/关闭事件和本补丁的其它渲染功能尚未参与本轮测试。

尤其不能简单使用 `Task.Run(() => Query(sourceNote, ...))`：查询仍读取 source 的 tempo/时间接口，异步任务期间源可能被编辑或关闭。下一阶段需要明确源快照与拥有者、请求代次、最新请求覆盖、Part 修改失效以及关闭时的取消和等待，之后才能在宿主中验证拖动。50 ms 等待预算和本轮同进程原生测试都不能替代这些约束。
