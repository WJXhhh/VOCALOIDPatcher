# xiang 尾部共享音素边界的音量凸起

2026-10-22。用户指出当前选中音符尾部圈出的区域有明显咔嗒声。本轮通过 MCP 读取现场，并从当前宿主缓存取得 PCM，复现并修复了该位置一个明确的处理缺陷：两个相邻音素分别做边缘淡化，导致交界处短暂恢复到原始音量。

## 现场对应与复现证据

MCP 捕获时工程 revision 为 185，目标为零基索引 Track 0 / Part 1 / Note 2，歌词 `xiang`、音素 `s\ iAN`、MIDI 65、VEL 64，后接 Note 3 的 `wang / uAN`。目标尾部的音素边界提前约 23.22 ms；`iAN` 的音量为 -6 dB，后续 `uAN` 为 -6.6 dB。两者共享边界：目标音符相对 tick 209，亦为下一音符相对 tick -31。

没有保存、切换或重渲染用户工程。MCP 当前连接没有暴露独立 timing 查询工具，使用已有 `query_project` 的 `timing_diagnostics` 显式投影读取边界及音素音量。在复制到私有诊断目录的缓存中，先以整 Part 18 个音符的时间/音高序列匹配目标 PCM，再核对原生与音素音量输出的样本关系。匹配文件的平均目标音高相关度约 0.981，其他候选约 0.39～0.46。

关键确认不是仅凭文件时间或波形外观：将读取的两个实际音量区间送入修改前的生产处理器，在共享边界前后各约 10 ms 的输出与当前宿主缓存 **逐样本完全一致**。当前宿主自动平滑缓存与音素音量缓存也完全一致，说明该凸起没有被后级消除。

旧增益的上升/回落各约 5 ms，形成约 6 dB 的窄凸起。它是多样本响度突增，不要求出现满幅削波或单个孤立的大样本跳变，因此前一轮围绕过渡音量阈值和孤立断点的检查没有覆盖到这个根因。

这项证据明确对应本次圈出的音素音量接缝，不能外推为此前所有“极端过渡方波”的统一解释。用户提供了咔嗒声的听感定位，本轮对真实 PCM 做数值复现和修复验证，尚未进行修复版的宿主试听验收。

## 修复

修改 `PhonemeGainWaveProcessor.ProcessWindow`：对取样后首尾相接的受控区间建立共享增益桥，直接在两侧目标增益之间作余弦插值。共享端点的两个独立淡回原音量操作被该桥替换。

- 共有的嵌套/重叠区间继续按原有乘法叠加；同一点多个结束/开始区间分别取两侧增益乘积。
- 桥宽受原有 5 ms 限制，并按音素长度和相邻共享端点间距缩短，避免密集桥重叠。
- 连续静音保持静音，连续相同增益不再在接缝处回到 0 dB。
- 不相接的区间继续在各自范围内淡化，未受控样本不变。没有修改持久化值、撤销记录、原生合成或时间轴。

6 项新增回归在修复前全部失败、修复后全部通过，覆盖 -6/-6.6 dB、同值衰减、连续静音、同值提升、嵌套公共增益、4096 样本流式分块边界和极短相邻静音区间。保留原有非相接/嵌套区间的乘积验证；旧测试中把相接区间各自淡回 1 当作预期的部分，改由共享边界行为断言覆盖。
