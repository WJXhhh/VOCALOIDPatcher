# 音素 timing 与过渡扩展的压缩组合（2026-10-18）

用户澄清的问题是：timing 拖动和值正常更新，但实际渲染声音不能继续缩短。不是滑杆的命中、可达范围或显示缓存问题。

## 复现与两个独立原因

同一个中文采样声库的单音素 `a`，先把入音 Begin 向前扩展 24 帧、出音 End 向后扩展 24 帧，再对称压缩音素两端。原音素范围为 172 帧，约 998.5 ms；压缩后为 6 帧，约 34.8 ms。

旧实现以固定秒数保存过渡端点位移。音素范围已经变短，过渡仍额外占据原来的 48 帧，形成声音长度下限。固定范围的 Phase 本身不增加几何范围，本次对照中没有同样的问题；历史 Onset 位移也存在固定额外时长的问题。

| 设置 | 压缩后 ART 总分配范围 | PCM 活动范围（峰值的 1%） |
| --- | ---: | ---: |
| 仅音素 timing | 69.7 ms | 68.9 ms |
| 旧的 ±24 帧过渡扩展 | 348.3 ms | 350.7 ms |
| 新的按音素范围缩放的过渡扩展 | 81.3 ms | 80.8 ms |

PCM 活动范围只用于声音对照，不等同于音素边界。没有剪裁、平移、归一化或后处理音频。原生入音、出音及帧量化本身仍占有范围，不能承诺声音长度等于 34.8 ms。

保存重开的压力回归另外发现：仍存活的旧 Part 的原生路由，可能通过已释放并被复用的 schedule 地址进入新的私有规划器。`bind_parser(..., None)` 原先只删除当前 parser 键，没有按 schedule 地址清除其他 parser 的旧绑定。结果基准规划已经被旧 timing 扭曲，VSM 无法关联基准音素位置。无过渡控制的压短工程也可触发，两套 SDK 均观察到，独立新进程重开同一文件则成功。

原生修正使**每个**新绑定引擎都先声明 schedule 所有权，包括没有 Part 控制的普通引擎及私有规划器。保留旧 Part 控制数据，清除的是失去内存所有权的旧执行绑定。测试覆盖旧 Part 仍然有效、不同 parser 复用同一 schedule、没有活动控制作用域的情况。

曾检查 DSE 初始化模式；成功与失败均观察到模式 0，强制调用其他模式初始化不能解决问题。该假设及试验改动已撤回，没有新增地址、哈希档案或 ABI。

## 控制数据与提交规则

`TransitionProjectTimingScale` 为端点和历史 Onset 添加可选参照：音素身份（稳定音符 ID、音素序号及符号）和编辑时的音素范围帧数。计算为：

```text
有效位移帧 = round(原始位移秒 × FPS × 当前音素范围帧数 / 参照范围帧数)
```

当前范围取原生基准音素边界经过**音素 timing** 后的长度，不从已经展开的过渡范围反推。共享接点保存一组完整别名和一个参照。以原生接点距离选择所属音素，不按名称寻找替代目标。其他 Part 及失去目标、保留供撤销的数据不参与迁移。

旧工程缺少参照时保持原来的绝对位移语义。仅打开、保存或修改 Phase 不迁移；第一次实际修改音素 timing 时，从修改前的范围建立参照，并与音素 timing 放在同一条共享撤销内。先验证包含共享边界候选及过渡控制的完整原生计划，再提交。不存在失败后丢掉控制、套默认值或裁剪成假成功的路径。

保存的是原始参照意图，不反复把量化后的帧数写回。压缩到有效位移为零时，意图仍保留；修改其他过渡的 Phase 或增益不会删除它。显式重置会删除该控制。再次扩展恢复原始关系。Phase 和 dB 保持原有独立语义。

组合提交合并 Changed 通知，统一推进渲染代次。历史压入失败时同时回滚两份文档。未知参照扩展字段仍以不可执行的原始数据保留；较旧补丁也会把新增字段视作未知扩展并保留，而非忽略后渲染。

## 验证与产物边界

- 最低 SDK 6.13.1.1 编译；6.13.1.1、6.13.3.1 使用各自真实 DSE/VSM 验证。
- 每套引擎连续三轮，每轮包含原始、Phase、端点、历史 Onset、全部组合的四档长度；另核对共享撤销/重做、压缩后保存重开、修改其他控制后保留亚帧意图、恢复原长的 PCM。
- 普通宿主矩阵另外覆盖共享接点、多 Part 并发、无关 Part 缓存、工程复制、未知格式及保存失败回滚；发音修改矩阵覆盖重新绑定、撤销和邻接上下文变化。
- 242 项托管测试、47 项 Rust 测试；全解决方案 Debug/Release 独立构建。Rust Release 的 linker stdout 被编译器作为 warning 转发，不是链接失败。
- 实际引擎回归使用优化后的 Release 原生 DLL。未将 Debug 原生 DLL 的宿主行为纳入验收。
- 候选和提交验证只调用局部规划，`CurrentFrame` 仍为 0，不请求音频。测试中的完整链路计时包含候选查询、提交验证及重新读取计划，不是单次原生调用耗时，也不是 MouseMove 热路径的计时。
- PCM 恢复对照沿用已记录的原生重复渲染数值包络：峰值差不超过 2 PCM16 LSB 且 RMS 不超过 0.1。该阈值只用于验证，不进入生产处理。

详细数值见 `evidence/transition-timing-compression-20261018.json`。2026-10-18 用户授权后已同时部署主补丁和包含路由清理的原生 DLL，保留原主补丁链接；安装文件、普通 Release 输出和备份均通过哈希核对。部署记录见 `evidence/transition-timing-compression-deployment-20261018.json`。未启动或关闭编辑器，实际界面操作仍待用户验收。
