# 第四段音素 timing 松手提交失败

2026-10-21，用户明确指定时间顺序上的第四个 Part（第 18～22 小节、24 音符）。通过 VOCALOID MCP 读取现场，并让用户在该段试拉一次，取得实际失败状态；没有改写用户音符或参数。

## 现场原因

宿主已加载前一轮 `bei` 修复，渲染服务启用、渲染完成、timing host 未暂停。第四段的 69 个音素边界在独立工程副本中均能完成预览查询，左右各移动一帧的 138 次预览也都成功。用户试拉后，MCP 的 `views[].phoneme_failure` 明确记录：

```text
commit: NotSupportedException: Transition planning requires a complete captured context (at most 33 notes), 44100/256 and native presend.
```

`SetPhonemePlan` 在提交音素修改前，需要保留并重新验证该 Part 已有的过渡控制。原实现复用针对被拖音符准备的局部窗口；窗口向两边最多各取 16 个音符。第四段虽然只有 24 个音符，靠近首尾的被拖音符仍拿不到完整段，因而 `QueryTransitions` 拒绝提交。预览可动不等于松手能写入。

把提交路径加入独立重放后，138 个方向候选中有 80 次精确重现“缺少完整上下文”；另有 3 次属于原有几何边界拒绝。并非所有位置都有同一种问题，不能用删除过渡控制或跳过提交验证解决。

## 修改

局部音素预览保持原路径。提交前的过渡验证复用 `PrepareTransitions`，以整段中间音符为中心，先获取完整原布局，再把候选音素计划（包括共享边界关联音符）传入同样的整段准备流程。中心音符本身命中候选计划或被重置时，也采用相应候选／中性计划。

33 音符、44100 Hz、256 采样 hop、原生 presend、源 revision、身份及原生几何限制均保持。归档格式、撤销事务及原生 ABI 未改变；未删除已有过渡、音素 timing 或工程数据。

## 验证

新增 `--stored-phoneme-replay`，直接读取已保存工程副本，复现预览与提交前的过渡重新规划。修复后 80 次上下文拒绝全部消失；69 个边界各有至少一个可提交方向，138 个候选中的 135 个通过。其余 3 个方向仍因过渡锚点压成零宽而拒绝，反方向通过；未放宽该检查。所有规划查询 Starts/Steps/Samples 为零。

再在独立副本中隔离第四段，重新映射归档定位，保留其音乐起点及全部 NOTE 数据。24 个音符逐一修改起始边界，并执行实际提交认证、原生路由发布和音频渲染，另有预热、原控制基准、恢复，共 27 次真实渲染。每次已消费 ART 来源与计划一致，原生 timing/gain Failures 为零；音符位置、长度、音高、VEL 和音素文本不变。24 次修改均确实改变 PCM，最后恢复结果与预热后的原控制基准逐字节一致。这里验证的是独立后端与提交协议，尚未替代 Editor 内鼠标交互验收。

310 项托管回归通过；完整解决方案 Debug/Release 隔离构建零警告、零错误。证据见 [回归汇总](evidence/part4-phoneme-commit-context.json)。原始 MCP、工程副本、日志与 WAV 均在仓库外。
