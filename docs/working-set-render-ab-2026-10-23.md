# 工作集修剪与后续渲染：A/B 实验

日期：2026-10-23。

本机随机三组确认中，工作集修剪使下一轮原生渲染的配对中位耗时增加约 **10.14 ms（2.63%）**，bootstrap 95% 区间为 **+1.51～+16.58 ms**。修剪 API 自身还需约 **11.23 ms**，未计入下一轮耗时。它有小幅负面影响，但本轮没有看到可据此解释秒级卡顿的证据。

这是独立原生渲染结果，不是 Editor 整体提速比例。最初固定顺序实验得到的较大差值混有环境/顺序波动，下面保留原始结论演进与全部统计，不把它们一律解释为修剪收益。结构化结果见 [实验汇总](evidence/working-set-render-ab-2026-10-23.json)。

## 范围

本轮测量独立进程内、实际安装的 VSM/DSE 原生异步渲染。测试进程只对自身调用 `EmptyWorkingSet`，不清理系统文件缓存，不修改其它进程，不改变用户设置或真实工程，没有部署、启动或关闭 Editor。

测试时没有运行的 Editor，VOCALOID MCP 实例列表为空。因此本报告不是完整 Editor 的 UI、派生后处理或导出延迟验收。

环境为 Windows、AMD Ryzen 9 9955HX（16 核 / 32 逻辑处理器）、约 15.2 GiB 可见物理内存。原生引擎和托管 SDK 使用安装的 6.13.3.1；各文件哈希随结构化证据保存。VSM 缓存容量设为 1 GiB。

## 输入与流程

- 两个当前可试用的 V5 中文声库：`Luo_Tianyi_Ning`（`BD79E492NWWK3DDF`）、`Luo_Tianyi_Wan`（`BL8CEAM5N4XN3LFK`）。MIKU V4X 的初次预跑输出静音，被非静音检查拒绝，未进入正式统计；没有修改授权状态。
- 每 Part 12 个相接的 `a` 音素音符，120 BPM，每个音符 480 tick，44.1 kHz。测试音高按确定的五音循环排列。
- 分别测全部音符和第一枚音符的音高编辑，只提交真实音高变化，不额外触碰 Velocity 或发送强制失效。每次必须观测到新 PCM 的 DSE Step 与采样诊断。单音符编辑不保证引擎只重算该音符，实际计算量另由计数记录。
- 每个场景预热四次，正式修剪场景做 30 对观测，即时空白对照另做 10 对。每对按 AB、BA 交替顺序，A 保留工作集、B 修剪工作集。每个观测之前都进行一次不修剪的 primer 渲染，以重新加热该场景的活跃路径。
- 实际修剪组：primer 完成后等待约 1000 ms，B 调用 `EmptyWorkingSet`，A 不调用；两组都在至少约 1250 ms 后开始下一轮编辑和渲染。
- 即时对照组在独立的一次进程运行中进行：primer 后立即编辑，两组都不执行修剪。这是尚未触发修剪时的空白对照，用于观察计时/顺序偏差；没有模拟“下一轮长渲染期间计时器到点”的宿主行为，也不直接用它与正式场景的绝对耗时相减。
- 每个场景中相同最终输入的全部 WAV 必须 SHA-256 一致；失败或静音直接终止实验，不作为快速样本。

主要计时从音符编辑开始，到原生完成回调已经泵送且 `IsFinishedRendering` 为真。单列编辑时间、异步渲染时间、修剪 API 时间、原生停止时间、工作集、Private Bytes、页面错误计数、进程 CPU 时间与可用物理内存。

1250 ms 人为等待、修剪 API、observer 建立/注册、指标快照、停止/清理与 WAV 验证不计入编辑至完成耗时。修剪本身也消耗时间，不能把它当成免费操作；它发生在本次人为等待中，故与下一轮耗时分列。

## 统计与证据

共完成 410 次纳入统计的观测：初始修剪对照 240 次、即时空白对照 80 次、随机三组确认 90 次。所有观测均通过非静音、新 PCM 计算和同场景 WAV SHA-256 一致性检查。另有不计时的 primer 和预热。

原始逐次 JSONL 和 metadata 留在本机 `v6patch-working-set-ab-20261023-122137` 隔离目录，汇总记录三个 JSONL 的大小与 SHA-256。早期包含额外强制失效的校准运行已中止并标记为预实验，没有纳入最终统计。初始直接编辑实验使用 metadata 版本 2，随机三组确认使用版本 3。

每种场景分别报告两组中位数/P95，以及同一对内 B−A 的中位数。配对中位差的区间使用固定种子 `20261023`、10,000 次有放回 bootstrap，取 2.5% / 97.5% 分位；这是当前样本条件下的区间，不代表其它工程/设备的保证。异常耗时样本保留。

页面错误计数不区分软缺页和硬缺页；进程 I/O 传输计数也不是物理磁盘读取计数，不能直接据此推导磁盘瓶颈。Private Bytes 与工作集分别报告，避免把移出驻留页面解释为释放了同样多的分配。

### 初始成对实验

两臂全局中位数如下，“差”是 B 中位数减 A 中位数；它与逐对差值的中位数不是同一个统计量。

| 声库 / 编辑 | A 保留 | B 修剪 | 中位数之差 | 相对 A |
| --- | ---: | ---: | ---: | ---: |
| Ning / 全部音符 | 432.75 ms | 450.59 ms | +17.84 ms | +4.12% |
| Ning / 单音符 | 418.62 ms | 450.16 ms | +31.54 ms | +7.53% |
| Wan / 全部音符 | 342.15 ms | 374.23 ms | +32.08 ms | +9.38% |
| Wan / 单音符 | 327.26 ms | 349.73 ms | +22.46 ms | +6.86% |

四组逐对差值中位数分别为 +30.08 / +30.18 / +16.70 / +16.32 ms，完整区间、P95、计算次数与内存见汇总。没有删除异常值。

但后续即时空白对照中，两臂均未调用修剪，Ning / 全部音符仍出现 +18.14 ms 的配对中位差，10 对同向，区间为 +12.43～+37.21 ms。这说明固定顺序和当前环境存在不能忽略的偏差。因此上表 **4～9% 不能直接认定为关闭修剪的因果收益**。

初始修剪实验期间可用物理内存最小约 14.23 MiB、中位约 598.01 MiB、最大约 4027.24 MiB，负载条件明显波动。空白对照与正式场景属于不同进程/时段，不能直接相减校正。

### 同条件随机三组确认：主要结论

针对异常出现的 Ning / 全部音符场景补做 30 个三元组。A 保留、B 修剪、C 假操作；三组都等待至少约 1250 ms，只有 B 在约 1000 ms 时调用修剪。六种排列各出现五次，再以固定种子随机打乱块顺序；原始 Position 验证了全部六种顺序的次数。

本轮时间为北京时间 12:44:57～12:48:00，可用物理内存约 1253.80～2812.90 MiB，中位约 2233.55 MiB。

| 组 | 编辑至完成中位数 | P95 | 渲染窗口页面错误中位数 |
| --- | ---: | ---: | ---: |
| A 保留 | 360.08 ms | 461.96 ms | 7,768 |
| B 修剪 | 372.95 ms | 461.80 ms | 30,600.5 |
| C 假操作 | 361.79 ms | 1115.19 ms | 8,097 |

三组 DSE Step 均固定为 4329，WAV 摘要均相同。计时差并非通过减少合成量或改变输出获得。

| 同一三元组内的差 | 差值中位数 | bootstrap 95% 区间 |
| --- | ---: | ---: |
| C − A | −2.38 ms | −11.20～+1.86 ms |
| B − A | +12.47 ms | +1.22～+16.95 ms |
| B − C | +14.51 ms | +11.00～+26.03 ms |
| B − (A+C)/2 | **+10.14 ms** | **+1.51～+16.58 ms** |

最后一行先在每个三元组内平均两个不修剪对照的耗时，再计算修剪额外耗时，最后取 30 组中位数；对应逐组相对增加的中位数为 **2.63%**。它不是上方三个全局中位数直接相减，所以数值不必相等。

假操作差的区间包含零，修剪对两个对照都表现为额外耗时，支持本机本次条件下的小幅负面影响。不过 C 组 P95 仍有明显尖峰，不能声称关闭修剪改善了尾延迟或解决全部卡顿。

B 组工作集中位数从约 105.22 MiB 降至 0.25 MiB，下一轮渲染后回到约 93.23 MiB；Private Bytes 修剪前后中位数均约 415.82 MiB。修剪调用自身中位耗时约 11.23 ms。工作集下降明显，但不等于释放了同等大小的私有分配，且之后会重新驻留活跃页面。

### 对产品策略的含义

速度优先时，值得避免在每次工程加载/乐段渲染完成后无条件修剪，保留最小化、手动操作或经过验证的内存压力策略。当前实验没有比较整个系统的长期内存压力和其它应用响应，不能据此要求所有情形永久禁用修剪。

本次没有改变默认值或用户开关。若后续调整策略，应在实际 Editor 中继续核对 UI 停顿、后处理并发、工程切换、最小化以及内存压力；本轮约 10 ms 的原生影响不能外推成整套 Editor 的固定提速率。

后续已按用户要求在源码移除渲染完成后的自动修剪，最小化时修剪保留，尚未部署；变更与下一层研究见 [重复渲染与失效范围定位](render-invalidation-research-2026-10-23.md)。

直接修改单音符时，Ning / Wan 的 DSE Step 约为 4291 / 4294，与整段的 4329 很接近。这个夹具中的单音符编辑并未呈现仅合成一枚音符的计算量，值得作为后续失效/增量渲染研究入口；没有额外强制失效，仍不能把这一现象直接外推到所有原生工程和声库。

## 复现

基准入口是 `voicebank/tools/evec_render_harness/WorkingSetRenderBenchmark.cs`，分析程序是 `voicebank/tools/analyze_working_set_ab.py`，没有新增依赖。

```powershell
$abArtifacts = Join-Path $env:TEMP ('v6patch-working-set-ab-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
dotnet build voicebank/tools/evec_render_harness/EvecRenderHarness.csproj -c Release --artifacts-path $abArtifacts

# 使用本机已经构建、匹配当前引擎并通过 ABI 检查的原生诊断 DLL。
$env:VOCALOID_TIMING_PROBE_NATIVE = (Resolve-Path 'native/playback-clock/target/release/v6patch_clock.dll').Path
$abOutput = Join-Path $abArtifacts 'paired-30'
& (Join-Path $abArtifacts 'bin/EvecRenderHarness/release/EvecRenderHarness.exe') $abOutput --working-set-render-ab --ab-pairs=30 --ab-notes=12 --ab-waits=1250
python voicebank/tools/analyze_working_set_ab.py $abOutput --output (Join-Path $abArtifacts 'summary.json')

# 同条件三组确认：保留、修剪、假操作，各 30 次，六种顺序均衡随机。
$abTriplets = Join-Path $abArtifacts 'randomized-triplets-30'
& (Join-Path $abArtifacts 'bin/EvecRenderHarness/release/EvecRenderHarness.exe') $abTriplets --working-set-render-ab --ab-pairs=30 --ab-notes=12 --ab-waits=1250 --ab-banks=BD79E492NWWK3DDF --ab-triplets --ab-all-only
python voicebank/tools/analyze_working_set_ab.py $abTriplets --output (Join-Path $abArtifacts 'triplet-summary.json')
```

可用 `--working-set-license-check` 只查询声库名称、ID 和授权结果，不输出密钥或序列号。可用 `--ab-banks=...` 选择声库，当前夹具默认使用上述两个中文声库；其它语言需核对夹具中的语言 ID。`--ab-waits=0,1250` 选择空白对照和实际修剪场景。输出目录必须全新。

## 解释边界

本实验针对“相同活跃渲染路径在一次修剪之后，下一轮需要付出多少成本”。共同 primer 会重新加热活跃路径，两个实验臂共享同一进程；它不能替代分别长期运行两套修剪策略的对照，也不能量出 Editor 的整个视觉树和所有插件被移出工作集后的恢复成本。

场景按顺序执行，交错配对只平衡实验臂顺序，没有随机化全部场景顺序或控制其它程序。当前机器的可用物理内存会波动，汇总保留其范围。不能把单机重复观测外推为普适提速百分比。
