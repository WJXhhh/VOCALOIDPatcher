# timing 两端拖动后的原生空帧崩溃

2026-10-17。用户报告崩溃前拖过音符 timing 的左右边界，工程未保存。本轮保留原始转储和日志于本机临时目录，不把用户工程、转储或日志加入仓库。用户随后要求部署，15:58 已替换原生 DLL 并独立核对哈希；未启动 Editor，宿主复验待用户进行。

## 现场与证据边界

Windows Application Error 记录 15:25:36，`VOCALOID6.exe`，DSE.dll 6.13.1.1，异常 `0xc0000005`，RVA `0x16B10B`。转储中故障指令读取 `[RCX+0x20]`，`RCX=0`，访问地址为 `0x20`。这是过渡交叉淡化预处理读取右侧帧所属采样段的位置。

转储中的左侧帧索引为 3491，右侧为 3492；右帧的段指针为空。转储没有收录完整调度堆，无法从中恢复那条段记录及未保存的两端控制值。因此下面的独立夹具复现的是已查明的同类非法状态，不宣称还原了用户的精确拖动顺序。

Ghidra 当前目标元数据和实际只读查询确认：DSE.dll，x64，映像基址 `0x180000000`，SHA256 `7A4965BD377DBC2B08710E807AE1345B67D9FFF6579CA0C01A769F744366F5B5`。下文地址均为该映像 RVA。

## 根因：返回地址桥接破坏了补帧识别

流式合成会在计划不足时，从 parser 的 `0x1B3A50` 调用静音包装器 `0x1A7310`，返回点为 `0x1B3A55`。这条路径补入的帧已经处于输出时间坐标，不应再次经过音素 timing 的源时间映射。普通音符前置静音则仍需要映射。

`phoneme_timing::allocate` 原来通过栈回溯识别这个返回点。独立选样功能安装的 `duration_bridge` 也拦截了静音包装器：它临时把栈上的返回地址换成生成的返回桥，原始地址保存在线程局部的调用记录中。因此两个功能同时开启时，栈回溯会漏认补帧。

补入的一帧被当作源时长压缩后，可量化为零帧。`0x1A7310` 的正长度检查发生在分配器调用之前；被 hook 改成零时已经过了检查。底层 `0x18B630` 仍会追加一条 begin=end 的段记录，但不填任何帧槽。后续 `0x16AF70` 处理交叉淡化时会读取该起点的右帧段指针，出现与现场相符的空指针读取。

## 修复

- `duration_bridge::original_caller` 读取当前线程中最内层匹配包装器的原始返回点，不依赖生成代码页的栈回溯。
- allocator 在运行期优先用该返回点识别输出补帧，保留其原始输出时长；独立安装 timing、没有返回桥时仍使用原有的真实栈识别。
- 普通静音和发音段继续执行原有 timing 映射。没有修改用户控制范围、设置开关、ABI 或工程格式，也没有在合成器崩溃处跳过段或钳制段长。

线程局部调用记录的单元测试覆盖嵌套同类/异类包装器、退出后的恢复，以及不同线程之间的隔离。

## 可重复验证

入口为 `EvecRenderHarness --timing-crash-probe --patcher-dse-initialization <输出目录>`，通过 `VOCALOID_TIMING_PROBE_NATIVE` 指定待测原生 DLL。必须逐个启动 SDK 探针进程；Part 并发测试在单个 SDK 进程内执行。

确定性补帧夹具使用中文单元音 `a`，两端各偏移 80 个原生帧。`VOCALOID_CRASH_SPLIT=1` 先按原生次序提交输入，`VOCALOID_CRASH_PADDING=1` 再从真实 parser 入口连续驱动八次输出补帧。探针在进入合成前检查段起点是否具有帧映射；发现非法状态时仅在研究进程中中止，避免为了回归故意触发访问冲突。

| 版本与组合 | 结果 |
|---|---|
| 修复前 DLL，选样返回桥开启 | 首次补帧产生 `[3413,3413)` 空段，起点帧无段指针，探针按预期失败 |
| 修复前 DLL，不安装选样返回桥 | 八次补帧均为一帧，通过 |
| 修复后 DLL，返回桥开启 | 八次补帧均为一帧，通过 |

`VOCALOID_CRASH_DURATION_HOOKS=0` 提供上表的无返回桥对照。`VOCALOID_CRASH_SCENARIOS`、`VOCALOID_CRASH_OFFSETS` 和 `VOCALOID_CRASH_BANK` 可指定单音素/接续/多音素、两端偏移矩阵和声库。

边界比较使用最终原生分配段的 begin/end/音素分割点，同时单独报告已合成区间的覆盖情况。短 SDK 夹具可能在延后的尾部被消费前就结束渲染；不能把尚未消费的边界报告成原生分配错误，也不能据此宣称已验证该尾部的完整音频。报告保留最终计划、已消费段及消费游标以便区分。

常规扫描与 Release 强制补帧扫描各检查 147 个请求组合：89 组在现有 planner 的有效范围内并全部通过，58 组由既有边界/拓扑约束拒绝，没有进入渲染。Release 扫描的 712 次补帧均保留一帧长度，最终分配的音素边界全部吻合；没有发现新的未映射接点。

最终 Release DLL 另通过独立选样与 VEL 0/127、浮点辅音系数、多音素 timing 的 20 次渲染，以及四 Part、三轮同时渲染与逐 Part 参考 PCM 的比较（12/12 PCM 相同，峰值三个原生修改作用域重叠）。验证数字和摘要见[证据文件](evidence/timing-output-clock-crash.json)。Debug/Release 解决方案构建、39 项 Rust 测试和 176 项托管测试通过；宿主内复验尚未进行。
