## 头字段由stream格式标记决定

`0x1801363a0` 的位22分支读取顺序是：

| 内容 | 帧对象偏移 | 条件 |
| --- | --- | --- |
| float A | `+0x270` | 总是 |
| float B | `+0x274` | stream `+0x2c == 0x32534d53`（SMS2） |
| float C | `+0x278` | 总是 |
| int count | `+0x27c` | 总是 |
| count组double三元组 | 第二共振列表 | count>0 |

所以三浮点头是SMS2格式上下文的结果，不应理解成原始分析文件相对最终DDB必然多一项。
当前商业主帧确实含三个float，现有独立解析器的物理布局仍正确。
通用stream构造器 `0x18012a3a0` 本身就将 `+0x2c` 初始化为SMS2，
不能以当前文件扩展名或是否嵌在SMS2顶层块内决定使用两个还是三个float。

## 实际原生实验

沿用文档45的帧构造器与通用块读取器ABI，在0x80字节清零stream上分别设置上述标记。
读取前将帧对象 `+0x274` 人工设为123.25，以检测缺字段时的默认行为。
自生成帧kind=1、time=0、mask=`0x400000`，第二共振为(200,0,200)。

| stream上下文 | 文件头float | 文件长度 | 读取后A/B/C | count |
| --- | --- | ---: | --- | ---: |
| 非SMS2（0） | -26.5, -0.125 | 64 | -26.5, **123.25**, -0.125 | 1 |
| SMS2 | -26.5, 73.5, -0.125 | 68 | -26.5, **73.5**, -0.125 | 1 |

两次读取返回0，count及三项对象字段符合分支预期。尤其非SMS2分支没有把B清零，
而是保留对象原值；复用帧时不能假定该字段自动获得默认值。

首次实验误把非SMS2上下文也写成三个float，独立字段断言失败；纠正格式后通过。
这同时说明读取返回0不能代替字段验收。
`0x180106e20` 在未设置stream `+0x1c` 的路径，会按块声明长度定位文件尾，
因此最终stream字节数等于文件长度也不能单独证明字段被正确消费。
本轮结论依赖实际对象字段和count，而不是仅依赖返回码、游标。
