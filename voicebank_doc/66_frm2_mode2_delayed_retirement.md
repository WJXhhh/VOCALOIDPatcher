# 模式2延迟退休及队列边界反例

2026-09-14，同文档65的DSE SHA256，重新确认Ghidra目标。

## 算法验证

1,024组`f1a80`对照全部一致，262组触发退休，160组明确给额外队列槽有效值。
覆盖索引0/1/2/5/9，100/200帧每秒，四档缺口阈值，已归属/未归属轨迹，
无效幅值及无数组帧。历史使用连续有效前缀及无效尾部，不触发内部缺口插值；
短轨迹删除关闭，以独立核对退休条件。

模型：`frm2_mode2_tracks.retire_from_history`。
验证与构造器布局检查：`verify_frm2_mode2_retirement.py`。
证据：[66_frm2_mode2_retirement.json](evidence/66_frm2_mode2_retirement.json)。

- 当前归属非-1的槽不退休。
- 队列索引<2时，无归属槽即时退休，与文档65一致。
- 索引>=2且cfg07>0时，从**queueIndex+1**逆向寻找最近有效幅值。
- 有效值须大于cfg03、不等于10000，并且该帧含对应槽。
- 找到后以`float32((queueIndex+1-lastIndex)/frameRate) >= cfg07`判断退休。
  阈值相等会退休；完全找不到有效历史时，反而不执行这一退休写入。
- 退休写入幅值10000、期望频率0、退休标志1。

## 生产布局不是任意增长队列

构造器`cdde0`将跟踪索引设置为`int(max(cfg06,cfg07)*frameRate)`，
再按预滚动和下游分析模式分配队列。此前增长队列实验用于覆盖算法索引条件，
不能直接等同于实际构造器的固定延迟布局。

本轮实际调用原生构造器：44100 Hz、跟踪模式2、cfg06=cfg07=0.03，
其余保持构造器默认值。整数分析模式位于配置`+558`，与跟踪模式cfg00不同。

| 分析模式 | 队列槽数 | 跟踪相对偏移 | 跟踪索引 | index+1槽已分配 |
| --- | ---: | ---: | ---: | --- |
| 0 | 3 | 0 | 2 | 否 |
| 1 | 4 | 0 | 2 | 是 |
| 2 | 4 | 0 | 2 | 是 |
| 3 | 3 | 0 | 2 | 否 |
| 4 | 8 | 0 | 2 | 是 |
| 5 | 3 | 0 | 2 | 否 |

因此不能假设所有分析模式都提供额外槽。验证脚本对这六种布局只构造和读取元数据，
**没有**对缺少额外槽的布局执行退休函数；算法矩阵则始终显式分配额外槽。
目前尚未证明这些缺槽配置能经过完整分析调度抵达该扫描，不把布局反例宣称为已复现崩溃。

此前直接调用`ef9f0`的验证不包含这一步；它须保留在整块未完成清单。
