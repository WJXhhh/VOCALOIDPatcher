# 相位分析入口：模式切换不能补齐缺失输入

2026-09-15，继续普通 FRM2 精确数值语义。

## 本轮确认

在本机固定DSE版本中，自有220 Hz稳态PCM直接进入 `d9b10` 批处理，仅打开配置ID `0x7d`，无法构成完整相位生产流程。六种分析模式与两种自动音高开关的24组对照已定位实际故障，而非仅根据空输出推测。

| 配置 | 结果 |
| --- | --- |
| phase关闭，mode0—5，各automatic0/1 | 12组全部完成，各44帧；没有bit37输出 |
| phase开启，mode1/2/4，各automatic0/1 | 6组在RVA `d762d` 读取空相位数组的首个float时失败 |
| phase开启，mode0/3/5，各automatic0/1 | 6组更早在RVA `d46ab` 读取队列节点的frame字段时失败 |

故障时受检相位队列帧均有正F0，但谐波数为0，频率、幅度和相位数组均不存在。对mode0/3/5，数组缺失是观察状态；真正首先触发的错误是队列访问，不能混称为相位数组解引用。

## 控制流依据

已复核Ghidra目标 `/v6/DSE.dll`，x86-64，基址0x180000000，SHA256与证据相同。仅在内存中查看少量原始指令，没有保存反编译代码。

- `d5639` 检查本次step取得的0x7d；非零直接跳至 `d619b`，跳过常规分析模式分支。
- `d691b` 后的条件在0x7d非零时跳过外层跟踪调用 `ef9f0`、`eff80`。
- `d6bfa` 后的条件同样绕过后续普通处理分支。
- `d7404` 后只有0x7d非零才进入本次研究的相位流程；`d7629` 取得frame+0x70，`d762d` 不检查空值就读取首相位。
- `d46ab` 属于更早的队列音高改写，早于谐波和相位消费。

这些条件解释了为什么仅切换mode和automatic仍不能接通。它们不证明所有未研究的外部调用协议都无效，也不能据此断言其它DSE版本没有可用的相位生产入口。

## 验证工具

`voicebank/tools/probe_frm2_phase_entry.py` 每例在独立子进程运行，60秒上限。Windows异常观察器只记录DSE内的访问违例RVA，始终返回CONTINUE_SEARCH，异常仍由ctypes正常报告；没有跳过故障指令、恢复执行或修改DLL。退出前移除观察器。探针不注入谐波、F0、控制量或历史初值。

批处理辅助函数新增可选 `phase_analysis` 参数，仅在显式传入时设置构造前的配置字段；默认行为保持原状。探针对两类已定位错误及关闭相位时的44帧基线均有断言，不把意外失败算作符合预期。

[机器可读证据](evidence/97_phase_entry_contract.json)。全部运行数据位于仓库旁研究目录，未使用Windows Temp。

## 对完成边界的影响

相位模型、给定初值的跨帧语义和保存/消费对照依然成立。尚未闭合的是没有额外输入适配的原生完整相位生产入口。本轮把“也许换个分析mode就能通”的不确定性收窄为：受检mode0—5均不能仅靠启用0x7d解决，下一步需要研究不同调用协议或接受独立生产实现的明确边界，不能继续无依据地扫描同一组开关。
