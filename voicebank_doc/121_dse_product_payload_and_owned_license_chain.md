# P 的生成与自制传统声库授权资源链

2026-10-16，接续[120章原生候选验收](120_dse_native_candidate_acceptance.md)。本轮将仍由夹具直接提供的 P，推进为**从自制 DDI 文件加载，再由原生产品表生成函数取得**；用于计算 Key 的 P 由独立 Python 槽位解码器预测，两者逐字节核对。

**标准 DBSe 自制传统声库的“资源文件 → P → 本机 Key → 原生 NoError”链已通过验收。** 20份自有资源、38次完整候选判定符合预期；15个现成传统声库的槽位数据另作只读比对，均能独立解出其70字节 P。证据见[484](evidence/484_dse_owned_resource_license.json)。没有部署或操作 Editor。

## P 不是从音频计算出来的一个统一摘要

传统路径为 `0x18010cf00 → 0x18010cfb0 / 0x18010d1f0`。正常已编译根的主路径，从 stationary part 四个32位整数中取出已存放的字节，按固定顺序旋转回去；不是对整个 DDI/DDB 或 PCM 做一个 MD5。

`0x18010cf00` 用根对象 `+0x1a8/+0x1b8/+0x1c0/+0x1c8` 的内部类型哨兵决定分支。根读取器把 magic 与正弦值写入 `+0x1a8`，随后与余弦及构造器的 ARR3/ARR4/DBSe 标记比较，门限 `1e-5`；这不是音频特征。自制标准 DBSe 文件实测进入下面的槽位提取路径。

另一个 `0x18010d1f0` 分支会检查各 part 的四槽是否全为 `-1`：全缺省时有16字节固定回退，遇到非缺省值时可进入时间种子派生的32字节数据路径。**不能把这个回退分支与标准 DBSe 的缺省行为混为一谈。** 本轮自制链验收限定标准 DBSe；不把其它根状态或 AI `.vtbr/.vtb2` 宣称为已恢复。

## 四个整数的精确用法

每个 STAp 的四槽在运行时为：

| 槽位 | 内存偏移 | 原生读取 |
| --- | --- | --- |
| `i0` | `+0x1f0` | 数据时只取低8位 |
| `i1` | `+0x1f4` | 数据时只取低8位 |
| `i2` | `+0x1f8` | 第一个 part 是完整有符号32位长度；后续 part 只取低8位数据 |
| `i3` | `+0x1fc` | 数据时只取低8位 |

遍历顺序是 stationary 组、PHDC音素 ID、匹配 STAu 内的 part；匹配使用 `0x18010a350`，不能只按名称猜顺序。槽位消费顺序如下：

```text
第一个 part: i2 = N；依次读取 i3, i1, i0
后续每个 part: 依次读取 i2, i3, i1, i0

每个数据字节 = rotr8(整数低8位, 1)
累计得到 N 字节时停止
```

反向写入时，把每个自有 P 字节 `rotl8(byte, 1)` 写进对应整数槽，第一个 part 的 `i2` 写完整长度 N。容量为 `4 * part_count - 1`；70字节需要18个 part，128字节需要33个 part。这解释了现成库为何出现“70字节”，并不是某种70字节摘要算法。

例如自有原始 P 为 `b"OWN"`，一个 part 的 `[i0, i1, i2, i3]` 为 `[156, 174, 3, 158]`。这一步的一位旋转，与普通授权后续的 `T^-1(P)`（两位旋转及 XOR）是**两层不同变换**，不能合并或少做一层。

原生产品表查询把 P 当零结尾字节串，遇到零会截断。当前生产缓冲区边界为128字节加终止零；新写入器限制长度及容量，并拒绝嵌入零，避免声明长度与实际参与 Key 的 P 不一致。

## 现有自制生成器的 P 实际为空

现有 finalizer 把四槽都写成 `-1`。加载有效 DBSe 后：

1. `0x18010cfb0` 读到首个 `i2=-1`，返回提取失败，没有写出数据；
2. 外层 `0x18010cf00` 忽略这个返回值，仍返回0；
3. 产品表生成器预先把输出区清零，因而为该组件建立**存在但 P 为空**的表项；
4. 归一化身份命中该表项后，授权比较实际使用空 P。

这是原生实测行为，不是主动跳过资源检查：自制 DDI 已加载，`authenticated=1`，原生表中组件身份正确，之后完整候选函数返回 `NoError`。

“表项存在但 P 为空”和“找不到组件表项”不同。后者保留查找 helper 的时间派生回退；120章已测得原 Key 不匹配。不能把 P 从任何产品的公式中一概删除。

当前自制生成器默认的全 `-1` 路线，已经足以用空 P 接上本机计算；非空 P 则可由自有资源槽位明确承载，不需要复制商业 P。

## 产品身份与文件路径

`0x180180850` 从已加载 singer 的路径取父目录名的前16字符，经过 `T` 后作为表项身份；实现入口为 `0x1801805d0`。本轮资源布局为：

```text
任意自有基目录/
  <规范化 CompID>/
    owned_p_resource.ddi
    owned_p_resource.ddb
```

普通比较按 C0 查表，因此物理组件目录身份须与 C0 对齐。`generate_v5_metadata.py` 已采用“注册 Path 基目录 + CompID 子目录”的结构。DDI/DDB同 stem 与 DBSe 的 stem 摘要是另一层格式检查，不能替代组件目录与产品身份的对应。

测试将资源移到另一有效 CompID 目录后：仍给旧组件身份/旧 Key，结果为 `InvalidKey`；改用新组件身份并重算 Key，结果为 `NoError`。资源内容 P 没变，说明组件身份这一项仍独立参与匹配。

## 从文件到结果的验收

本轮没有导入商业素材，声学资源由生成的220 Hz正弦产生：44.1 kHz、13230个源采样，经已有 DRS 工具得到52帧，形成自有 DDB。33个诊断 STAp 引用这份同一自有单元；这是结构与计算夹具，不是训练完的歌手音质验收。

验收链为：

```text
自有PCM → SMS2 → DDB + 33-part DDI
                  ↓
独立槽位解码预测 P
                  ↓
原生 CDBSinger 从文件加载，authenticated=1
                  ↓
原生槽位提取 + 原生产品表生成，均与独立 P 相同
                  ↓
按 S/C0/H/T^-1(P) 计算 Key
                  ↓
原始完整候选函数 → 公开 License.Result
```

与120章相比，本轮没有手工填充传入的原生产品表。资源枚举容器及 VDM descriptor 输入仍由进程内适配器提供，实际文件加载、P提取、产品表生成和许可判定均调用未修改的原生实现。

| 验收项 | 结果 |
| --- | --- |
| P长度0/1/2/3/4/7/15/16/31/32/64/70/71/127/128，以及另一128字节序列 | 16份资源的独立解码、原生提取及产品表全部一致 |
| 所覆盖 P 字节 | 1–255全部非零字节值 |
| 上述每份资源的正确 Key / 改动 Key | 16次NoError / 16次InvalidKey |
| DDI槽位 P 改变，保留旧 Key / 重算 Key | InvalidKey / NoError |
| 数据槽高24位改变、低8位不变，首长度不改 | P及Key保持有效 |
| 目录组件身份不对应 / 对齐后重算 | InvalidKey / NoError |
| DDB中一个自有PCM采样位改变、DDI槽位不改 | P不变，同一Key仍NoError |
| 超长度、容量不足、零字节、错误根/PHDC、巨大帧数及截断输入 | 9项在原生调用前被作者工具拒绝 |
| 合计 | 20份资源、38次候选判定：NoError20、InvalidKey18 |

改变 P 的测试是在文件上改槽后重新加载，不是改加载后的字段；提取代码及候选判定代码前后哈希相同。DDB采样改变的结果只证明这里的 P 与这项 PCM 内容无关，不推导为所有声学资源校验都不存在。

另以本机15个传统库的原生加载字段，按实际遍历顺序收集槽位，再用独立槽位算法解码：全部首长度70、消费18个 part，与原生产品表 P 一致。这里只记录ID、长度、part数和相等关系，未保存商业P或音频；3个AI库不在该比较范围内。
