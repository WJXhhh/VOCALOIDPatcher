## 先区分参与计算的量

| 记号 | 含义 |
| --- | --- |
| `C` | 当前产品的原始 CompID，16字符 |
| `C0` | `decode(C)` 的 payload 索引7置字符 `0` 后重新编码的16字符 ID |
| `S` | 普通 descriptor 的 SerialNumber，必须通过同一16→14 codec；参与摘要的是原编码字符串 |
| `H` | 单个硬件候选字符串，每次比较只用其中一个 |
| `P` | 按 `T(C0)` 查询产品数据表后得到的原始字节串 |
| `N` | 比较双方共用的内存上下文后缀 |
| `K0` | 基础32字符 Key；62字符时为 `K[:3] + K[33:]` |

`T` 是逐字节变换，所有中间位运算取8位：

```text
T(b)    = rotl8(b XOR 0x1b, 2)
T^-1(b) = rotr8(b, 2) XOR 0x1b
```

原生 `0x1801dc130` 与独立实现的19组输入完全一致，包括0–255全部字节、嵌入零、MD5填充边界和较长输入。普通/Splice 两个产品归一化 helper `0x1801d83b0`、`0x1801d9740` 各通过4组独立 codec 对照，其中包含非零索引7。当前18个安装库的该位原本均为0，不能仅凭这些安装库检验归一化的效果，也不能据此命名该位的业务含义。

## 普通分支的实际比较

定义 `md5hex(x)` 为 MD5 的**小写十六进制 ASCII 文本**，长度32字节，`||` 表示字节连接。主循环 `0x1801df557–0x1801df6bb` 的数据顺序为：

```text
V = T(S) || T(C0) || T(H) || P

Key侧  = md5hex(K0 || N)
数据侧 = md5hex(md5hex(T^-1(V)) || N)
       = md5hex(md5hex(S || C0 || H || T^-1(P)) || N)
```

这里的 `S/C0/H` 都是字符串的原始字节；不是其14位 payload，也不是解出的十六进制二进制。内层 MD5 的32字符文本参与外层 MD5，不能改成16字节二进制 digest。

因此，在产品数据查找成功的这个分支中，令 `K0` 等于内层 `md5hex(S || C0 || H || T^-1(P))`，就能构造两侧一致的自有计算样例。这个等式是已验证的计算关系；本轮没有把样例写入安装元数据或让完整 DSE 分支接受新组件。

原生调用与独立算法的对应为：

| 原生地址 | 作用 | 通过数量 |
| --- | --- | ---: |
| `0x1801e0a70` | 普通 `md5hex` | 19 |
| `0x1801e2a60` | 对输入逆变换后计算 `md5hex` | 19 |
| `0x1801e0390` | 原字节摘要，可附加 `N` | 38，分别覆盖开/关 |
| `0x1801e04f0` | 逆变换后的内层摘要，可继续附加 `N` 计算外层摘要 | 38，分别覆盖开/关 |
| `0x1801d7ba0` | 普通 Key 侧；62字符时移除索引3起的30字符 | 32/62两种形状各1 |
| `0x1801e0070` | 把上下文32位计数格式化为 `%08x` 后 MD5，并递增计数 | 4 |

`N` 位于上下文 `+8` 的字符串里；时间参与初始状态，但同次比较两边共用它。它不是需要另找的一把持久化私钥。48组普通正例覆盖不同自有 `S/C0/H/P` 组合和两种上下文，原生 `0x1801d9b90` 返回距离0；分别改动 `S/C0/H/P/K0` 的240个负例均超过原生 `1e-5` 门限。

**普通 S 与产品的关系现在可以说得更准：** 此路径先分别检验 C 和 S 的 codec，再把二者一起纳入摘要。没有看到要求 `S == C` 或逐位把 S 当产品 ID 比较的操作。共用格式只证明编码兼容；S 由谁分配、各业务位是什么意思、是否对应购买序列号，仍不能从这段本地代码推出。此比较中没有调用 Splice 的 Ed25519 验签函数，不能继续用“公私钥匹配”概括它。

### 硬件候选的精确字符串

`0x1801d8030` 的第一项来自 `SHGetFolderPathA(CSIDL_WINDOWS)` 所在卷，经 `GetVolumeInformationA` 取得32位卷序列号：

```text
H_volume = ASCII("fe00" + format(volumeSerial, "08x"))
```

若得到的序列号为0，代码用固定值 `0xad626448`。随后 `GetAdaptersInfo` 按枚举顺序取每个非空地址，逐字节 `%02x`，不加冒号或连字符，形成额外候选；不要求网卡处于连接状态。

独立 Win32 查询和格式化与原生列表逐项、按顺序一致：本机1个卷候选、5个网卡候选，共6项。脚本不输出或保存这些字符串。循环逐项尝试，不能表述成“磁盘与全部网卡合在一起绑定”。

### 62字符 Key 的日期

匹配摘要之前，`0x1801d7ba0` 从索引3移除30字符，留下基础32字符。摘要匹配后才继续日期处理：

- 起始日期输入是 **VDM VoiceBank.Date**。主循环持有的 `R12` 来自声库 vtable `+0x38`，本机18个声库都与公开 `VDM_VoiceBank_date` getter 相同；不是普通 S。
- `0x1801dc200` 解码这个日期 ID，把 payload 索引8开始的末6位解释为十进制 `YYMMDD`，年份基于2000，交给本地 `_mktime64`，时分秒及 `tm_isdst` 置0。不能把它当 UTC 时间戳或严格日期格式验证器。
- `0x1801d9c20` 从 Key 索引32向4每次退2位，把当前位置及前一位组成十六进制字节，依次恢复15字符，前置 `B` 得到16字符到期日期 ID，再调用相同日期 helper。
- 主调用点检查 `start <= now <= expiry`，满足时内部11经 getter 对应 `ValidExpiryKey`，否则内部1对应 `ExpiredKey`。这些结果来自静态调用链，未运行完整 expiry 候选。

直接日期及62字符嵌入日期分别用4个自有日期（含闰日）与 Python 本地时间计算对照，8项完全一致。32字符成功路径直接形成 `NoError`，不走此期限判断。

## 两条路径共用的产品数据 P

之前缺少的输入来自资源加载流程，不能只凭 C/S/H 或 descriptor.Key 解释全部计算：

```text
VDM数据库 → DSE资源初始化 → 产品数据表 → 按T(C0)查询P
```

`0x180180850` 构造表；表项步长146字节，前16字节是变换后的组件标识，`+0x11` 开始为数据区。查询 `0x1801d86f0` / `0x1801d9890` 按字节读到零或最多129字节。原表由初始化调用者释放；不能把 manager singleton 中曾存放的指针当成长期有效表。验证脚本在独立进程初始化后重新构造快照，使用完释放，不改全局指针。

可追溯的来源包括：

- 传统库 `0x18010cf00 → 0x18010cfb0 / 0x18010d1f0`，从已加载 stationary 资源字段提取，或进入派生/回退路径；
- AI 库 `0x180183160`，读取 `.vtbr/.vtb2` 资源，处理文件内容及128字节尾部；不能简单说 P 就是整个文件或它的单一 MD5；
- 产品查找失败时 helper 先保留时间派生的回退数据；本文普通公式的稳定产品输入及实测均以成功命中为条件。

当前快照有20条查找记录；18个声库全部成功命中归一化身份。它们读出的 P 都长70字节，共17种不同内容。因此 P 不是保证唯一的身份，70也只是此安装的观测值，不是通用格式上限。20条查找记录与18库、29个 descriptor 是不同计数。

**P 的生产算法尚未完全脱离 DSE 实现。** 当前独立完成的是组合与摘要算法，P 仍通过本机资源读取 helper 获得；未导出真实 P、专有查找表或反编译实现。自制资源如何在全部提取/回退条件下产生预期 P，还需要独立样本验证。

## Splice 摘要现在可复现

定义 `I = UTF8(IceProductName)`；本机声库分支的准确组合是：

```text
IceValue = hex(SHA256(A || I || B || UTF8(C) || P || D))
```

这里用原始 C；P 通过归一化身份查询，但放入 SHA-256 的是其**原始表数据**，不做普通分支的逆变换。也没有把 H 或普通 S 加进此摘要。descriptor.Key 虽经过辅助计算，没有在这段最终 SHA-256 拼接中作为输入；不能把它直接当 IceValue 或 lease 公钥。

`A/B/D` 各25字节，由标准32位 MT19937 分别以 `123456789 / 987654321 / 20240601` 为种子，从 DLL 内250字节池中按输出 `% 250` 选择。脚本只在内存读取当前哈希对应 DLL 的有界初始化区，不包含或导出池内容。独立 MT19937 与原生 `0x1801dbb20` 在这3个种子及4个边界/对照种子上全部一致。

拿该组合计算本机 asa，SHA-256 与其64字符 `IceValue` 解码后的32字节完全相同；单独改动产品标识字节后不相同。这比“找到了 SHA-256 调用”多了一次真实附加字段的计算回环。

摘要通过后仍须按 `IceProductName` 寻找 `.lic`，经过结构、时间、身份和 Ed25519 验签，详见[481的 Splice 专项](17_dse_license_pipeline.md#splice-专项三道本地检查与实际公钥)。本轮闭合了那里的摘要组合未知项，没有得到签发私钥，也没有把摘要通过当成 lease 有效。

## 复现与验证边界

运行[只读计算验证脚本](../voicebank/tools/verify_dse_license_calculations.py)：

```powershell
python voicebank/tools/verify_dse_license_calculations.py
python voicebank/tools/verify_dse_license_calculations.py --installed
```

默认只跑自有输入与隔离 helper；`--installed` 另读硬件、初始化本进程 VDM/DSE、构造产品表、比较本机 Splice 附加字段。使用64位 Windows Python，不加 `-O`；脚本在调用原生地址前强制检查两份 DLL 的精确 SHA-256，不兼容版本直接停止。`DSE_AUDIT_EDITOR` 仅改变查找目录，不取消哈希检查。

输出只有计数与布尔值，不输出真实 Key、普通 serial、硬件标识、P 或 Ice 字段内容。没有写注册表、安装元数据或 lease 的代码，没有启动/关闭/注入 Editor，没有修改 Ghidra 项目。完整普通候选激活、Editor 宿主验收、P 的独立生产和真实 lease 仍未由本轮实验覆盖。
