## 四条实际路径

1. CSMSAnalysis构造器 `cdde0` + 原生批处理 `d9b10`。
2. CSMSRegionAnalysis构造包装 `956b0` + 原生批处理。
3. CSMSAnalysis + 直接PCM push `d1140`、step虚方法、输出提交和收尾。
4. CSMSRegionAnalysis + 同样的直接流式协议。

区域类的step包装 `95730` 先调用 `d2cc0`，成功后才进入额外输出hook。它没有在分析核心之前补齐谐波。已复核活动Ghidra项目、DSE哈希与映像基址，查询与实验均未修改安装DLL或Ghidra。

直接流式实验绕开的是批处理调度函数，使用同样的原生输入、分析和输出接口；**没有**跳过任何相位分析指令，没有注入谐波/F0，也没有设置差分历史的特殊初值。它是调用协议对照，不是文档94的输入重放旁路。

## 新确认的ABI与收尾契约

输出提交虚方法+0x18接收 `(analysis, frame)` 两个指针。反编译伪代码曾省略第二参数，RVA `da020`—`da037` 的真实指令明确把context+0xcc8送入RDX再调用。只传analysis会提交错误帧。

流式运行需要与批处理一致地初始化PCM环、队列时间和输出时钟；输入按128样本推送，step按32位返回值判断是否需要更多输入。末尾判据使用1e-8秒容差；错误使用0.0005会少输出一帧。本轮以完整44帧及F0/掩码等输出元数据摘要相等验证了这些契约，不能只以“函数未崩溃”算成功。

## 96组对照

四种协议各覆盖6个分析模式×2个automatic开关×phase开关。每例独立子进程，60秒上限。

- phase关闭：48组都完成，各44帧。四种协议对应案例的完整返回元数据哈希相等，包含逐帧F0、掩码、谐波数和有效槽数量；此处不是PCM音质比较。
- phase开启：48组全部失败。模式1/2/4在 `d762d` 读空相位数组；模式0/3/5在更早的队列节点或frame解引用处失败（`d46ab` 或 `d46af`）。无效队列内容受内存布局影响，不能强行要求总在同一条相邻指令崩溃。
- 所有受检失败帧的谐波数量为0，频率、幅度、相位数组均不存在。记录中保留原始故障RVA，不把错误吞掉或继续执行。
