# Piapro EVEC 音素标签中的竖线

2026-09-10。只读核对用户现有 Ghidra GUI 中的 PPS.dll；目标版本、SHA-256、
架构及基址与 `32_evec_piapro_render_timing.md` 所列 PPS 一致。

## 已确认的显示路径

- `0x101ffe80` 构造音符标签，调用 `0x10202510` 取得音素文本，再用 `[%s]`
  包裹并送往文字绘制路径。
- `0x10202510` 在存在分段事件时先读取对象 `+0xfc` 所指事件的 `+0x4c`
  文本；对象 `+0x100`、`+0x104` 的事件存在时，分别先追加分隔符，再追加
  对应事件的 `+0x4c` 文本。没有分段事件时读取原始事件 `+0xbc`。
- 分隔符常量地址 `0x1072e15c`，文件原始字节为 `7c 00 00 00`，即
  UTF-16LE 的 `|` 和终止零。标签中的两处引用在 `0x102025e2`、`0x10202612`。
  `0x100357c0` 是读取终止零并追加字符串的辅助函数。
- `0x102216e0` 调度分段，分别以索引 1、2 调用 `0x102227c0` 构造/更新
  Color 和 Release 事件；后者按 `0xfc + 4 * index` 读取对应事件指针，
  使用各自起点、长度和音素文本。与标签读取的两个续接事件位置一致。

因此，截图中的竖线是真实的显示字符，表达内部事件边界；不是一个需要发音的
音素，也不是仅凭字体或网格造成的视觉错觉。此结论针对上述标签构造路径，
不泛化为所有文件格式、所有音素编辑入口都可以任意删除 `|`。

## 截图的解释

按截图可读文本，示例可分为 `t t#2 e`、`e#2`、`*#1` 三段：

| 显示内容 | 解释 |
| --- | --- |
| `t t#2 e` | 起音段，包含 Mild/Soft 的辅音起音处理 |
| 第一个 `|` | 起音段与 Color 续接事件之间的显示分隔符 |
| `e#2` | Soft 彩色延音 |
| 第二个 `|` | Color 与 Release 事件之间的显示分隔符 |
| `*#1` | Breath-Short 收音 |

设置图的 Consonant Extension 为 none；不能把 `t t#2` 推断成用户选择了 x2。
蓝色 S、右端短收音图标与 Soft、Breath-Short 选择一致。编号语义仍以对应
声库的 articulation 配置为准，不跨声库硬编码。

## 对 V6 适配的约束

显示时可以把多个事件摘要为一个逻辑音符；合成时应保留真实分段与各段时间。
不能仅把整串复制到一个音符，也不能认为去掉竖线、换成空格就恢复了 Piapro
行为。`32` 中的分段规划方向得到显示路径交叉验证，但这不证明 V6 的最佳
过渡时刻已经确定，更不证明听感已通过。此轮没有修改或部署生产合成代码。

反编译存在错误的 non-returning 推断：`0x10202760` 有大量不可达块警告，
不能据其截断输出断言辅音扩展算法已完整还原。早先搜索到的三处
`push 0x7c`（`0x10200296`、`0x1020dde7`、`0x1020e167`）实际是分配大小，
不作为竖线证据。
